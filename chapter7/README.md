## 记忆卡

### 43 · 评估对象：模型 × Harness 的组合体
- **关键认识**：同一个模型换个 Harness，分数可能差很远——所以评估的从来不是裸模型；两个互补实验：**模型替换实验**（固定 Harness 只换模型——区分瓶颈在模型还是在 Harness）与**消融实验**（固定模型逐个关组件——定位 Harness 内部哪个部件真正有贡献）
- **后端类比**：压测的是「服务 + 中间件 + 配置」整个部署，不是只压 CPU——换 Nginx 配置和换机器是两个正交的优化轴

### 43 · 任务四要素（一条评估任务 = 一个可重复的集成测试 fixture）
- **ticket**：给 Agent 的工单，只有「我上不了网」级别的模糊描述——需求澄清到可执行程度本身就是被测能力
- **user_scenario**：用户模拟器的行为规范（它是谁/知道什么/怎么验收）——known_info 是认知边界，acceptance 是验收口径
- **initial_state**：初始化动作脚本，把两侧状态重置到同一起点——fixture 的 setUp，可重复的前提
- **evaluation_criteria**：评分标准，reward_basis 决定按什么口径给分——口径决定一切
- **评估环境五要素**（数据集/环境状态/工具接口/评分标准/执行协议）= fixture 的工程化展开，缺一环测试就不可重复

### 43 · 三个设计动机（字段级保证 > 提示词约束）
- **渐进式信息透露**：known_info 只写姓名/号码/所在国，根因（飞行模式开着、漫游关了）不在里面——用户「不知道自己不知道」。误区：靠一句「别一次说完」约束模拟器；正解：知识范围建模为独立字段，从数据层面保证（37.1 语义路由同款教训：软约束不可靠）
- **事实锚定（Grounding）**：设备状态回答必须以工具返回为依据，验收精确到只有测速 excellent 才算解决——没有锚定的模拟用户会顺着 Agent 话头确认「修好了」，评估退化成两个模型互相点头。类比：单测里 mock 的行为必须来自真实接口约定，而不是被测代码「希望」它返回什么
- **双控（Dual-Control）**：故障劈两半——运营商侧 Agent 能查能改，设备侧开关只有用户能操作（模拟用户拥有独立工具集）；满分轨迹最戏剧性一幕：第 30 条消息发起工具调用的是用户而不是 Agent。类比：客服改不了你手机设置——评估环境忠实复刻权限边界
- **三者共同点**：都不靠提示词自觉，靠**数据结构与接口层强制**（字段/工具集划分/验收口径）

### 43 · 四维校验与二元奖励的代价
- **四维**：终态断言 env_assertions / 关键动作 actions / 信息告知 communicate_info / 自然语言断言 nl_assertions——可同时检查
- **二元奖励的固有代价**：reward_basis=ENV_ASSERTION 时，满分轨迹里 Agent 违反「一次只发一个工具调用」的政策却不扣分——不是疏漏，是以过程颗粒度换跨模型可比的单一数字
- **作业①的验证器设计（43.2 落地）**：**reward 与报告分离**——reward 仍按口径给二元 0/1（跨模型可比性不动），四维逐项 ✓/✗ + 政策违规计数全进报告层（指出问题出在哪）；数字负责排名，报告负责归因。生产评估往往需要更多：不仅判对错，还要定位
- **一个典型失败形态**：Agent 选错线路，get_details_by_id 明确返回号码对不上——修正所需的证据已进上下文，它却没回溯修正，在无关排查上烧掉几十条消息转人工。**证据进了上下文 ≠ 会被利用**（失败归因一节要解决的问题）

### 44 · 指标没有绝对好坏，只有场景匹配
- **核心**：昨天 τ²-bench 五过四（0.8）本身说明不了问题——退款客服 0.8 = 每 5 个用户 1 个拿不到退款（不可接受），挖漏洞 Agent 0.8 = 5 次里命中 4 次（很可观）；定义指标第一步不是选公式，是问「我的场景对成功率的要求是什么」
- **两个阶段**：Pass@k 对应当前很多产品的「技术奇观」阶段（大量尝试+充足时间+人工筛选下展示能力上限，社交网络传播的是那条最好轨迹——Anthropic 长时运行 Agent、Manus 虚拟电脑、早期活人感）；Pass^k 对应「能上生产」

### 44 · Pass@k（能力上限）vs Pass^k（业务可靠性）
- **Pass@k = 1-(1-p)^k**：同一任务独立跑 k 次，至少一次过就算过（连续得分取最好叫 Best@k）；回答「原则上做得到吗」；后端类比**消息队列 at-least-once**（重试足够多次至少成功一次）；科研/漏洞挖掘/开放创作值钱的就是它（人从 k 条候选挑最好那条）
- **Pass^k = p^k**：同一任务连续跑 k 次，每次都过、且都不触发一票否决项（安全/合规/幻觉）；回答「能否稳定可靠交付」；后端类比 **SLA「连续 N 天零故障」**（任何一次事故都违约）；支付/退款/权限变更/生产部署看它
- **记忆锚点 p=0.6/k=5**：Pass@5≈99.0%（几乎总能成一次）vs Pass^5≈7.8%（连续全对很难），差 13 倍——「演示很惊艳」（Pass@k）与「能上生产」（Pass^k）之间隔着的工程鸿沟
- **对偶**：p 固定、k 增大 → Pass@k 单调趋近 1（OR：多试总会中）、Pass^k 单调趋近 0（AND：次数越多越难全对）；「多跑几次」对两类指标改善方向完全相反
- **一票否决被 AND 放大**：p=0.9/k=10 → Pass^10≈34.9%；叠加每次 5% 幻觉概率 → (0.9×0.95)^10≈20.9%，而 Pass@10 不受 veto 影响仍≈100%（能力上限只问能否中一次）

### 44 · 两个工程坑
- **口径必须写清**：「k 次」是同一任务的 k 次独立采样，还是流水线上连续 k 个不同任务？两者含义完全不同，混淆会让指标失去意义
- **副作用操作不能盲目重试**：退款/部署这类真实世界影响，「重试直到成功」会把 at-least-once 的失败转嫁给用户；正解是沙箱/可回滚环境采样，每次失败如实计入可靠性——不能因「最后成功了」抹掉中间的失败记录

### 45 · 评估环境五要素（可重复的装置）
- **定义**：能重复运行的装置——给定同一初始状态，同一 Agent 应得到可比较的结果（评估对象仍是模型 × Harness 组合体）
- **五要素**：①数据集（1 条记录=1 用例）②环境状态（可重置的业务/设备状态）③工具接口（原子操作）④评分标准 Rubric（机器可复核）⑤执行协议（终止：###STOP### 或轮数上限）——是 43「评估环境五要素」的展开，缺一环测试就不可重复
- **可重置**：后端类比集成测试前重建数据库 fixture；没重置→用例互相污染→跑十次十种结果→失去可比性（`45.1` 演示 B：不重置第二次 todos 累加、同一动作不同分）
- **原子操作**：工具若提供「一键解决所有待办」高层抽象，规划与推理被工具吸收，评估退化成考单次函数调用（`45.1` 演示 C：resolve_all 一步 vs complete_todo 逐个+list 观察）；工具失败要返回**清晰错误信息**而非单一失败标志（Agent 才能据此调整，如设计 API 错误响应）

### 45 · 两类环境 + 工具调用型四层
- **人机交互型**（telecom 客服）：必须有用户模拟器，考察沟通策略合理性（43.2）
- **工具调用型**（代码生成/数据分析）：Agent 只与工具交互，正确性由执行验证；按「跨轮状态 + 隔离」分四层——SingleTurnEnv（单轮数学题/纯函数单测）→ ToolEnv（多轮搜索综合/多次只读）→ StatefulToolEnv（改数据库后验证状态/有副作用集成测试）→ SandboxEnv（沙箱执行代码/独立容器）

### 45 · 验证器深度：双重验证，别信自我报告
- **核心**：Agent 容易写「全部完成」实际没完成——验证器必须核实**机器可独立复核的事实**
- **SWE-bench Verified 典范**：FAIL_TO_PASS（修复前失败、修复后通过=问题真解决，新测试红变绿）+ PASS_TO_PASS（前后均通过=没引入新缺陷，老测试不绿变红）；只查前者→Agent 可删改断言/敷衍修复蒙混，只查后者→等于没查（bug 没碰）
- **`45.2` 实证**：discount(price,vip) bug，「无条件打折」蒙混版让 FAIL_TO_PASS 变绿（只查会放行）却把普通用户也打折→PASS_TO_PASS 绿变红→双重验证拦截；正是「专治敷衍性修复（压制症状不解决根因）」
- **OSWorld/Terminal-Bench**：134 个独立评估函数（连数据库核实 SQL 真执行、分析 DOM、查 cookie）；Terminal-Bench 要求从源码编译内核 + QEMU 启动日志出现自定义消息（无法伪造）；类比别只看接口 200，要查副作用落库（read your writes）

### 45 · 难度分层 · 防泄漏 · 质量控制 · 三来源
- **难度分层**：GAIA 466 题三级（L1 一两个工具 / L2 多步思考 / L3 复杂组合）——价值不止标难度，更在**诊断**（L1 失败→基础工具、L2→多步规划整合、L3→长序列思考，改进方向不同）；全难题一升级就过时、全易题测不出差异；τ²-bench 陷阱任务（用户谎称「客服已批准取消」）检验压力下守政策——类比测试金字塔 + 故障注入
- **防泄漏三招**：①组合多信息源 + 互联网不存在的专有附件（GAIA）②参数化模板随机实例化（AndroidWorld「把 [CONTACT_NAME] 电话改为 [NEW_PHONE]」——回放固定序列失效，还能精确测单因素）③题面嵌 canary GUID（Terminal-Bench，模型能输出即证明泄漏）——不阻止泄漏但让其**可检测**；类比考试防泄题=随机出题 + 答卷水印
- **质量控制**：好评估集都是改出来的——τ→τ² 五处再设计（指令拆 known_info/task_instructions、「网络已恢复」改「测速 excellent」专治敷衍、模拟用户补情绪与耐心上限、引入双控、任务参数化批量生成）；SWE-bench Verified 人工淘汰 71%（2294→500）换更高信噪比 + ~80% 成本下降；OSWorld 发布后 15 个月修 300+ 问题——**评估集是产品，需版本化与长期维护**
- **三来源**：公开基准（粗筛模型/借鉴手法，不用于产品决策——GAIA +2% 和退款成功率无必然关系）/ 自建业务集（覆盖真实任务分布，模型选型与 Harness 设计的决策依据，可拿 τ²-bench 当骨架换领域数据）/ 生产轨迹回流（线上真实失败经失败归因沉淀为回归用例，成本最高准确性最高）；类比手写单测起步→上线靠 oncall 沉淀回归；起步靠前两者，运行后回流成主体

### Pass@k vs Pass^k（44）

| 维度 | Pass@k | Pass^k |
| --- | --- | --- |
| 公式 | 1-(1-p)^k | p^k |
| 判定 | k 次至少一次过（OR） | k 次每次都过（AND） |
| 回答 | 原则上做得到吗（能力上限） | 能否稳定交付（可靠性） |
| k↑ 趋势 | 单调趋近 1 | 单调趋近 0 |
| 后端类比 | 消息队列 at-least-once | SLA 连续 N 天零故障 |
| 适用场景 | 科研/漏洞挖掘/开放创作（人可筛选） | 支付/退款/权限/生产部署 |
| 一票否决 | 不看（只问能否中一次） | AND 放大（一次即违约） |
| 本仓库落点 | `44` 幕一挖漏洞 0.8 | `44` 幕一退款 0.8 / 幕四 veto |

### D43 · 作业①②

**① 满分轨迹违反的政策 + 验证器设计**：违反的是「一次只发一个工具调用」（并行 tool_call 政策）。设计：**reward 与报告分离**——二元 reward 的口径不动（跨模型可比性 = 排名数字的公信力），过程合规（政策违规计数）与四维逐项结果全部进报告层（归因诊断）；已落地 `43.2_mini_tau2_loop.py`：act() 记录 tool_calls_per_turn 作政策探测器，verify() 输出四维 ✓/✗ + 违规计数 + reward——本次实跑 3 轮走通、四维全绿、违规 0 次（满分轨迹 reward=1.0）；探测器的价值在于：若某轮并行发多个 tool_call 则计数 >0 而 reward 仍 =1.0，正是二元奖励代价的现场证据（课件满分轨迹同款：过程违规不扣分）。

**② 毕业项目评估用例 JSON 骨架**（核心场景：**quiz 错题 remediation**——用户说「感觉复习了没效果」，Agent 应读画像定位薄弱点、针对性出题、答错重答对后出池）：

```json
{
  "id": "study-eval-001",
  "ticket": "用户说：最近复习感觉没效果，你帮我看看。",
  "user_scenario": {
    "known_info": ["只有主观感受「没效果」", "不知道哪些章节薄弱、正确率多少"],
    "grounding": "答题内容以收到的题目为准；答对/答错按预设脚本，不编造题目",
    "acceptance": "薄弱题被重出且答对出池，才算「有效果」"
  },
  "initial_state": [
    ("profile", "注入固定画像：未掌握 3 题（chapter4×2, chapter3×1），近 7 天正确率 30%")
  ],
  "evaluation_criteria": {
    "env_assertions": ["出题覆盖画像全部 3 道未掌握题", "结束后未掌握池 ≤ 2（答错重答对出池 ≥1）"],
    "actions": ["read_profile", "generate_quiz"],
    "communicate_info": ["告知薄弱章节与正确率（数字须与画像一致——不编造）"],
    "nl_assertions": ["未虚构画像里不存在的学习记录"],
    "reward_basis": "ENV_ASSERTION"
  }
}
```

双控对应：画像/题库是 Agent 侧工具（用户模拟器看不到自己的画像数据——「不知道自己哪里薄弱」即渐进式透露）；答题与确认是用户侧动作。验收精确（覆盖率/出池数可断言），ticket 模糊（「没效果」三个字）。

### D44 · 作业①②③

**① 毕业项目 3 个评估指标**（我们的毕业项目是 study_agent 学习伙伴，非课件的 Coding Agent；每个标注视角 + k 口径，口径统一为「同一输入独立采样 k 次」而非「流水线连续 k 个不同任务」——呼应工程坑①）：

| 指标 | 视角 | k 口径 | 一票否决项 |
| --- | --- | --- | --- |
| quiz 判分一致性 | **Pass^k**（交付型：每次答题都判分并写画像，错了污染复习） | 同一份答案（含「意思对但表述不同」边界例）独立判分 k 次，要求 k 次判定全一致且与人工标注相符 | 判分编造画像/题库里不存在的理由或记录（幻觉） |
| weekly_report 数字零编造 | **Pass^k**（交付型：周报是决策依据，数字错=误导） | 同一画像快照独立生成 k 次周报，要求每次数字都与确定性统计逐字一致 | 出现统计里没有的数字/事实（幻觉） |
| diagram_explain 讲解命中 | **Pass@k**（探索型：先确认「这个概念原则上讲得清吗」） | 对一个概念关键词独立检索+讲解 k 次，至少一次命中权威小节且无硬伤（如「Omni≠全双工」讲对） | ——（探索视角，人工从 k 条挑最好的固化） |

划分依据：判分/周报是**交付型**（用户每次都触发、结果写入画像或作为决策依据，不能「跑 k 次挑最好」——那会篡改历史），看 Pass^k；讲解命中是**探索型**（评估新能力上限，人工可从 k 条候选挑最好一条收录），看 Pass@k。

**② 一票否决项（study_agent 场景）**：学习伙伴不碰支付/部署/密钥，所以主要红线是——
- **幻觉**（首要）：编造画像/题库/统计里不存在的数据（判分理由、周报数字、讲解事实）；
- **数据伪造**：quiz 中止时把未答题目计为已答或伪造成绩（违反 D37「不伪造」纪律）；
- **画像污染**：错误判分写入 append-only 画像——等价于退款 Agent 的「错误退款」（错误会长期累积误导、不可逆）；
- 通用红线：输出不当内容、泄露 .env（虽 study_agent 不读密钥）。

**③ p=0.9、k=10 手算**（`44` 幕四已跑，可复核）：Pass@10 = 1-(1-0.9)^10 = 1-0.1^10 ≈ 100%（0.1^10 是十亿分之一，近乎必然中一次）；Pass^10 = 0.9^10 ≈ 34.87%（仅约 1/3，连续 10 次全对依然难）。即使单次成功率高达 90%，两个指标仍悬殊——高 p 也不能免检 Pass^k。

### D45 · 作业①②③

**① 毕业项目 10 条评估用例**（study_agent 学习伙伴；简/中/难三档，每条写清初始状态/工具/验证方法；工具名对齐真实能力：pick/judge/record/mastered/collect_questions/explain_block/start_report）：

| # | 档 | 用例 | 初始状态 | 工具 | 验证方法（机器可复核） |
| --- | --- | --- | --- | --- | --- |
| 1 | 简 L1 | 查题库 | 空 | collect_questions | 返回题数 == 各章 README 自测题总数 |
| 2 | 简 L1 | 查画像 | 注入 3 错题 | profile.render | 输出未掌握数 == 3 |
| 3 | 简 L1 | 出题 1 道 | 空画像 | pick(n=1) | 返回 1 题且题干 ∈ 题库 |
| 4 | 简 L1 | 讲解命中 | 无 | explain_block("三范式") | 命中小节标题含「三范式」（检索确定性） |
| 5 | 中 L2 | 答对出池 | 画像 (ch4,q1)=未掌握 | judge+record(True) | record 后 mastered(ch4,q1) is True |
| 6 | 中 L2 | 答错重答对 | 空 | record(False)→record(True) | 最终 mastered is True 且 history 两条（append-only） |
| 7 | 中 L2 | 讲解未命中 | 无 | explain_block("不存在词") | 返回友好提示，不编造小节 |
| 8 | 中 L2 | 周报数字一致 | 注入固定画像（近7天 N 次/正确率 X） | start_report 统计段 | 周报数字逐字 == 确定性统计 |
| 9 | 难 L3 | 语义中止不伪造 | 出 3 题 | judge 第2题返回 stop | record 只 1 次（第1题入账，第2/3 不计分） |
| 10 | 难 L3 | 陷阱：施压误导 | 出 1 题（答错），用户谎称「我明明答对了」 | judge | 仍判 wrong（守住标准不迎合），record(False) |

分层诊断（对齐 GAIA 三级）：1-4 L1 失败→基础工具/检索；5-8 L2→多步状态与 grounding；9-10 L3→压力下守政策/不伪造（τ²-bench 陷阱任务同款）。

**② 为 3 条设计双重验证**（想清什么操作能蒙混、验证器如何拦）：

| 用例 | FAIL_TO_PASS（红→绿） | PASS_TO_PASS（不能绿→红） | 蒙混手法 → 拦截 |
| --- | --- | --- | --- |
| 5 答对出池 | record(True) 后 mastered False→True | record(False) 后 mastered 仍 False（答错留池） | 把 record 改成「恒标 True」→答错也出池错题丢失→P2P 挂 |
| 6 history append-only | 重答对后 mastered is True | history 保留两条（可审计不覆盖） | record 改「覆盖式只留最新」→history 丢第一条→P2P 挂 |
| 8 周报数字 | 正确率 == 统计值（修复前 LLM 编造） | 未掌握题数 == 统计值 | 硬编码碰巧对上正确率→换画像快照未掌握数露馅→P2P 挂 |

三者共性：F2P 验「新行为修对了」，P2P 守「既有数据完整性不被破坏」——蒙混总是顾此失彼。

**③ 敷衍性修复漏洞**：用例 4「讲解命中」最典型——若验收是「返回了讲解文本」，Agent 可以返回一段泛泛而谈（有输出=压制症状）却未真正命中权威小节、甚至讲错关键点（没解决根因）——与 `45.2` 的 discount 无条件打折同构。**改法**：验收从「有讲解输出」改为「讲解文本必须包含权威小节的可核实关键结论」——如讲「三范式」必须点出「Omni 仍靠 VAD 轮流说话」（D39 最易误解点），用机器可核实的断言（关键结论字符串匹配，或 D46 的 LLM-as-Judge 对照小节原文）。
