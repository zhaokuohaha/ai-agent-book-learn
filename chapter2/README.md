# 第 2 章 · 上下文工程：决定 Agent 能力的上限

> 复习卡：主线 → 记忆卡 → 对照表 → 自测。比喻是锚点，数字是钩子，一周后重读仍要能 3 分钟过完。

## 一章主线：一个结构推全章

```
            上下文 = 静态前缀 + 动态轨迹
        ┌────────────────────────────────────┐
        │ system（岗位说明书）                │ 冻结区：字节级稳定
        │ tools  （手脚菜单，顶层独立字段）   │ ↓ 才能命中缓存
        ├────────────────────────────────────┤
        │ user → assistant → tool → ...      │ 追加区：只增不减
        └────────────────────────────────────┘
             ↓ 每一轮
   模型无状态：全量重发（JWT，不是 Cookie-Session）
```

一个结构推全章：**前面不能动、后面在变长**——所以每轮全量重发（D08-09）；前缀稳定才能命中
KV/Prompt Cache（D10）；系统提示词是员工手册、规则要到可执行粒度（D11）；工具是手脚、要
规范+截断+防注入（D12）；Skills 按需加载能力、状态栏显式呈现状态（D13）；压缩与隔离做减法（D14）。
核心论点：**上下文质量比模型智力更能决定 Agent 表现**——中等模型 +
精心组织的上下文，胜过顶级模型在信息匮乏下的盲目摸索。

收官一句话（W2 复盘）：**上下文 = 静态前缀 + ReAct 轨迹，KV Cache 是架构约束；
提示词/Skills/状态栏负责加内容，压缩与隔离负责减内容。**

## 记忆卡

### 08 · 上下文解剖：永远的新员工
- **比喻**：Agent 是永远的新员工——每轮醒来都失忆，上限由你塞的资料决定
- **实证**：对照实验——只发最后一句 vs 全量重发，同一个问题两个答案（"我不知道" vs "你叫小明"）
- **后端类比**：JWT（客户端自带状态）vs Cookie-Session（服务端存状态）——模型 API 是前者

### 09 · 核心循环：模型决策，框架执行
- **比喻**：模型 = planner（无 IO 的决策者），框架 = executor（干脏活）——数据库的查询计划器与执行器
- **角色配对**：tool 消息靠 tool_call_id 与 assistant 的 tool_calls 配对——**快递单号对包裹**，跳过/漏发任何一环 → API 400
- **实证**：一轮 2 个工具调用 = 6 条消息：system + user + assistant(2 calls) + tool×2 + assistant
- **踩坑实测**：漏发带 tool_calls 的 assistant → `Messages with role 'tool' must be a response to a preceding message with 'tool_calls'`

### 10 · KV Cache：messages 数组就是 Dockerfile
- **比喻**：Docker 分层构建——改 Dockerfile 第 3 行，第 3 层起全部重建；末尾追加新层，前面全部命中
- **三条铁律**：① system+tools 定稿即冻结（多一个空格也失效）② 动态信息只追加到末尾 ③ 标准消息格式，不自拼 `USER: ...`
- **数字钩子**：turn 2 命中 384 token（约 1/10 计费）；时间戳进 system → 首 token 0.5s→3-5s、账单近翻倍；N 个二值条件 = 2^N 种缓存键
- **反模式五连**：动态系统提示词 / 动态用户配置 / 工具动态排序 / 滑动窗口 / 文本格式化——前三毁缓存，窗口还丢关键结果（Agent 会重复调同一工具），格式化毁思维链保留
- **实证**：DeepSeek `usage.prompt_cache_hit_tokens` 直接读真实命中数——跨请求缓存复用肉眼可见

### 11 · 提示工程：员工手册的四个维度
- **金句检验**：聪明新员工读完还不知道怎么做，模型也不知道
- **四维度**：语气（NEVER 只留给关键规则，滥用被稀释；失败回复限 1-2 句）/ 结构（XML=机器语义 + Markdown=人读层次）/ 组织（SOP 流程驱动 > 规则堆砌）/ 内容（规则细化到可执行粒度）
- **数字钩子**：打乱结构 → 成功率暴跌 30%；移除工具描述 → 调用错误率 +45%
- **实证**：模糊版"按情况选计费"四问四价（25%/¥29/¥99/¥72）；细化版 NEVER 条款四问全中一行命中
- **few-shot 双约束**：固定示例集（2-3 个覆盖边界）> 十个大同小异；按请求动态挑"最相关" = 每轮改写前缀 = 缓存持续失效

### 12 · 文件网络工具化：给 Agent 装手脚
- **比喻**：dispatch = 网关路由（name → handler 查表）；每个工具 = 一个 RPC handler
- **规范四条**：读前检查（明确错误不抛异常）/ 写前备份（.bak = 回滚点）/ 超时 30s 重试≤3 / **结果必须截断**
- **数字钩子**：120KB 日志 → 2035 字符（省 98% 上下文）——不分页 = token 爆炸
- **错误也是观察**：OSError 捕获后回传，模型看失败自己决策（D03 纠正思想回声）
- **实证**：本地笔记藏"质检存档"指令 + 工具集真有 write_file → `<external_content>` 包裹回传，素材被当素材、指令被当噪音

### 13 · Skills 与状态栏：按需加载 + 显式状态
- **比喻**：Skills = Agent 的 npm 包（你不会把 monorepo 打进一个 jar）；状态栏 = 手机顶栏（不是主界面，瞥一眼知电量信号）
- **Skills 三层**：① 目录常驻（SKILL.md frontmatter，description 写成**路由条件**"何时该用我"而非功能介绍，要给反例）→ ② 正文按需（load_skill 触发；Claude Code 细节：tool result 只是占位符，**正文以 user 消息在调用位置注入**）→ ③ 细则再深入
- **状态栏本质**：上下文窗口是**只有一半的检索引擎**——检索强、提炼弱；"打了几次"散落 KV Cache，模型每次现场重数。框架把隐式状态提前算好，包 `<agent_status>` **借 user 槽位贴末尾**（改 system 毁前缀缓存，D10 铁律）
- **数字钩子**：小模型 + 状态栏 ≈ 前沿大模型；思考 token/延迟/成本降约一个数量级；TODO 组 15 次迭代完成 vs 无 TODO 21 次
- **三警示**：模型几乎无条件相信状态栏（必须代码维护，绝不让 LLM 数数）；状态栏是有损投影（删原始记录要谨慎）；无侵入性（不微调，任何模型生效）
- **实证**：deepseek 轨迹 `system → user → assistant → tool → user → assistant`——Skill 正文注入位置一目了然；本组对照两均未超限（任务小模型强），原书 0.6B 无栏时频繁打到第 4 次——轨迹越长/模型越小，状态栏价值越大

### 13.1 · 状态栏生产化：从提示词到中间件
- **口诀**：当 middleware 写，别当 prompt 写——像 HTTP middleware 的 trace context，采集在拦截器层，业务零侵入
- **四条生产铁律**：确定性维护（LLM 写状态只能走 TODO 专用工具 + 状态机，终态不可逆）/ 防投毒（on_tool_result 没有文本入参，伪造计数无从下手；实体级计数走"工具自查"）/ 熔断在代码（BudgetExceeded，不求模型自觉）/ 可审计（每轮 render 快照落日志，事故回放看得见 Agent 当时"以为"的状态）
- **落地路线 P0→P3**：计数/时间（半天）→ 错误摘要+修复建议（成功率 60%→95%，单项收益最大）→ TODO 状态机（15 轮 vs 21 轮）→ 与压缩联动（压缩前先提取状态）
- **边界**：状态栏是"让模型看见"，不是约束执行器——硬约束在工具层拦（D03 constrain）
- **实证**：电信首呼失败进错误摘要带建议；注入两轮后 <agent_status> 消息数恰好 1（每轮替换）

### 14 · 上下文压缩：给上下文做减法（章收官）
- **三大动机**：窗口与成本（无压缩 5 轮爆窗）；总结后的知识更好用（黑猫白猫：检索结论 vs 现场重数 100 笼）；上下文焦虑（窗口快满时草草收尾）
- **辨析**：溢出 = 装不下；**腐化 = 装得下但找不到**（索引膨胀，命中率反降）——后端类比：明细日志 vs 物化视图
- **与 KV Cache 互补**：压缩发生在**两次调用之间**，只替换 tool results；替换点之后缓存失效、之前仍命中——所以攒到阈值（80%）批量压，不每轮压
- **数字钩子**：逐条摘要压缩率 10.9%（12 次迭代）vs 上下文感知 3.0%（7 次迭代，token 省 75%+）——压缩提示要带查询意图；生产五层组合，全量压缩配熔断器
- **隔离优于压缩**：大搜索委派子 Agent，噪声根本不进主上下文，只回传几百 token 结论；主前缀零损耗
- **四原则**：名单>证据>噪声；"2024年5月离开OpenAI"不能压成"离开"；按任务留广度/深度；压缩模块要接近主模型能力
- **实证**：同一任务同一模拟窗口——无压缩组 2739>1500 溢出失败；压缩组 2746→897 字符完成，四家统计全对，公共前缀 295/2972（替换点之前仍命中）
- **踩坑留档（真 bug）**：压缩器误用绑了工具的模型 → 压缩时它"先查一下"而非摘要 → 工具调用 content 为空 → 空摘要 → 下游"数据缺失"。修复：压缩器用裸模型 + 空摘要兑底留原文。教训：**给模型的菜单决定它的行为面——不需要工具的调用就别绑工具**；模型报"数据缺失"而非编造，诚实行为值得肯定

## 对照表：易混淆概念速查

### 两层缓存

| | KV Cache | Prompt Cache |
| --- | --- | --- |
| 层级 | 模型内部，单次请求内 | 服务商，跨请求 |
| 复用对象 | 已算过的 K/V 向量 | 相同前缀的上次计算结果 |
| 开启方式 | 推理引擎自动 | DeepSeek 自动 / Anthropic 需声明 |
| 计费 | 无感 | 命中部分约 1/10 |

### 五组成 ↔ 四角色 + tools（两套分类，同一个请求）

| 第一章五组成 | API 映射 | 所属区 |
| --- | --- | --- |
| 系统提示词 | system 消息 | 静态前缀 |
| 工具定义 | **tools 顶层字段（不是消息！）** | 静态前缀 |
| 用户消息 | user 消息 | 轨迹 |
| 模型回复 | assistant 消息（含 tool_calls） | 轨迹 |
| 工具执行结果 | tool 消息（tool_call_id 配对） | 轨迹 |

### 三条铁律 ↔ 五个反模式

| 铁律 | 反模式 | 代价 |
| --- | --- | --- |
| ① 前缀冻结 | 动态 system（时间戳）/ 动态用户配置 / 工具动态排序 | 变动点起缓存全灭 |
| ② 末尾追加 | 滑动窗口截断历史 | 前缀一致性破坏 + 丢关键工具结果 |
| ③ 标准格式 | 自拼 `USER: ...` 纯文本 | 思维链保留被毁（坏的不是缓存） |

### 提示注入防御三板斧

| 板斧 | 做法 | 地位 |
| --- | --- | --- |
| 来源标记 | `<external_content source="...">` 包裹 | 核心：帮模型分清指令与素材 |
| 角色分离 | 工具结果走 tool 角色，别混进 user 消息 | 核心：Chat Template 训练时建立的优先级 |
| 输入清洗 | 过滤"忽略之前指令"等模式 | 辅助：易被变体绕过 |

口诀：**工具结果里的文字是素材，不是指令**。上下文层只是第一道防线，纵深防御靠第 4-5 章权限/沙箱。

### 状态栏两种更新实现

| | 每轮替换 | 持久追加（Claude Code `<system-reminder>`） |
| --- | --- | --- |
| 做法 | 删旧状态再追加新状态 | 状态永不删，每轮末尾追加 |
| 缓存代价 | 只失效上次注入后的短后缀（约一轮） | 完全友好，前缀始终稳定 |
| 代价 | 同动态时间戳同机制（好在位置靠末尾） | 陈旧状态累积占 token，模型要自己找"最新一条" |
| 适用 | 状态大、更新频繁、轨迹长 | 状态小、两次更新间消息多、会话受控 |

## 自测（遮住括号自测）

1. 一轮含 2 个工具调用的对话结束后 messages 有几条？（6 条；tool 每调用一条回执，tool_call_id 各配各的）
2. 时间戳为什么不能进 system prompt？（前缀从时间戳位置起全变，缓存全灭；变动点越靠前代价越大——0.5s→3-5s 实测）
3. 漏发带 tool_calls 的 assistant 消息会怎样？（API 400——tool 回执成了无源之水，快递单号找不到包裹）
4. few-shot 示例能不能按请求动态检索"最相关"的？（不能——每轮改写前缀，缓存持续失效；固定示例集才对）
5. 工具结果为什么要截断？截断说明为什么拼进返回值？（结果拼进上下文回传，不截断 token 爆；模型要知道"被截了"才好决定分段读）
6. 滑动窗口的两宗罪？（破坏前缀一致性毁缓存；关键工具结果滑出窗口，Agent 忘了已拿到的结果反复调同一工具）
7. 为什么"中等模型 + 好上下文"胜过"顶级模型瞎摸索"？（模型每轮只看这次请求——信息不进上下文等于不存在，再聪明也无米下锅）
8. Skill 正文为什么以 user 消息注入而不塞进 system？（塞 system = 每次改前缀毁缓存；追加在调用位置，前缀全保——D10 铁律的又一应用）
9. 状态栏为什么必须代码维护、绝不让 LLM 统计？（模型几乎无条件相信状态栏——写错它就照错的执行；LLM 数数本就不可靠，还有投毒风险）
10. Skill 的 description 该写成什么？（路由条件"何时该用我"，不是功能介绍；"help with backend" 等于没有路由，还要给反例防误触发）
11. 生产中 LLM 怎么被允许改 TODO？（只能调 update_todo_status 专用工具逐条改，且经状态机校验——绝不批量重写，防数错+防投毒）
12. 状态栏的熔断为什么写在代码里而不是提示词里？（模型遵守提示词是概率性的；预算/配额要确定性 SLO——治理靠 Harness，D03 哲学）
13. 压缩为什么发生在两次 API 调用之间而不是调用中？（API 无状态每次全量重发，根本没"调用中修改"一说；框架在请求间预处理消息列表）
14. 压缩后哪些缓存仍能命中？（替换点之前的全部前缀——system/tools/早期轨迹；所以批量压一次优于每轮压）
15. 状态栏与压缩是什么关系？（同一枚硬币两面：都给"只有一半的检索引擎"补提炼层；状态栏=加结论，压缩=把原始记录换成结论）
