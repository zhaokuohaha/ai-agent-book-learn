## 记忆卡

### 29 · 全景：为什么核心是 Coding Agent（概念日）
- **比喻**：W1-W4 学的上下文/记忆/工具是器官，今天开始拼完整机体——躯干是 Coding Agent，文件系统是循环系统
- **适用边界**：论断针对开放任务（产物形态多样的调研/生成/数据处理）；客服这类任务空间封闭的产品，核心仍是固定业务流程，代码只是工具箱一员
- **文件系统中枢**：OpenClaw 用 MEMORY.md + 按日期归档 Markdown，故意不用向量库——用户能直接打开改（记错了删一行）、天然保留时间顺序、可走 Git 版本控制回滚（「把状态存进可审计可回滚的 git 仓库，而不是黑盒数据库」）；Agent 能写文件 = 具备沉淀经验、修改自身外部产物的技术前提（持续进化的伏笔，第 9 章）
- **工程化六阶段**：项目文档化 → 需求澄清 → 设计文档 → 实现+测试 → 自我审查 → 文档同步。项目指令文件（CLAUDE.md/AGENTS.md）= 项目级系统提示词，会话自动注入、内容稳定，天然 KV Cache 友好前缀（D10/D13 回响）；设计文档是人类最佳介入点——审查一份文档远比审查几百行代码容易；现实按需裁剪（修 bug 直接进实现）
- **Harness 四件套**（W1 公式的 Coding 落地）：验收基线（什么算做完——测试/CI）/ 执行边界（能碰什么——权限/模块边界）/ 反馈信号（自动对错——lint/测试）/ 回退手段（怎么恢复——git/沙盒/快照）。「目标清晰度 × 验证自动化」四象限里代码任务天然在最佳象限——Coding Agent 成熟度最高不是模型特别强，是软件工程几十年的基础设施天然构成强 Harness
- **约束优先于指导**：能 Linter/CI 强制的规则就别写在提示词里请求（「做不了」远强于「建议别做」）；第二层目的是防过程性错误——删库重建「结果对了过程是灾难」，rm -rf 这类危险动作要专门拦截，约束的是动作而非仅仅结果（D26 执行边界回响）

### 29.1 · 七件套：通用 Agent 的全套手脚
- **比喻**：D28 的 3 工具配齐到 7 件——一个最小文件系统 API + 受限 shell，承载几乎所有任务
- **为什么七个不是八个**：理论上一个 bash 就够（OpenAI Codex 就这么干），拆七件让调用更精准——模型说「找文件」直接 glob，不用 bash dir 再解析输出（D24 回响：七个远够不到规模门槛，描述清楚比数量少更重要）
- **五分类落位**：感知三件（read/glob/grep）+ 执行四件（write/edit/bash/py_exec）；协作/事件触发/用户沟通不是 Coding Agent 的核心（第 6 章）
- **伴生三技巧**：行号标注读（「4→code」精确引用行号，后续 edit 更可靠）/ old→new 精确编辑（Claude Code/Codex/Cursor 现行方案：唯一即成功、不唯一或找不到即报错，绝不模糊匹配——22.4 参数保真回响）/ 写后即时语法检查（py_compile——IDE 红线思维，错误在引入当刻可见）
- **实证**：grep 定位 TODO → read 带行号 → edit 修分母 bug → edit 消歧失败（"return" 出现 2 次不改文件）→ write 缺括号当场 SyntaxError → py_exec 验证 average([2,4])=3.0（修复铁证）。实现沉淀 common/coding_tools.py（make_tools(ws) 工厂闭包绑定工作区，29.2 与 D30 复用——common/memory_store.py 先例）

### 29.2 · 测试-修复循环：「测试通过」才算完成
- **比喻**：完成标准从「代码写完」换成「测试通过」——Coding Agent 最常见的偷懒就是不跑测试就报告完成
- **确定性闭环设计**：预置带 bug 的 stats.py + 必失败的 test_stats.py——初始状态确定失败，Agent 必走「跑测试 → 失败输出回填 → 读代码 → edit 修复 → 再跑 → 通过」
- **错误变输入（工具层恢复）**：测试失败输出原样回填 ToolMessage（不终止会话）；幻觉调用收到「工具不存在 + 可用清单」；工具异常同样结构化喂回——「反馈越结构化越好」（与 D26.4 Sidecar 拒绝回执、27.3 HITL 回执三处同构）
- **system 注入（AGENTS.md 微缩，作业②代码落点）**：项目约定（edit_file 局部修改、测试通过才算完）进 system、任务指令精简为两句——任务文本不再提「用 edit_file」，模型仍走 read → edit → bash 测过的路径：约定从 system 生效（D11 信任分层：项目级约定 vs 任务级指令；D10 稳定前缀回响）
- **实证**：三次运行轨迹各异（先 bash 撞失败→修复 / 先 read 探查；system 版直接 read→edit→测过）但闭环结构一致；模型曾自发用 py_exec 加测边界（空序列抛 ValueError）——超纲的自觉；终检以落盘测试为准，不以模型自评为准
- **首跑翻车记**：终检 subprocess 漏设 PYTHONIOENCODING——agent 轨迹里 bash 返回正常「全部测试通过」，终检却 GBK 乱码误判「仍失败」；子进程读中文必须带编码环境变量（与 bash 工具同款处理）

### 29.3 · 故障恢复：分级升级、熔断与死亡螺旋
- **比喻**：恢复手段按对用户透明度分级——像急诊分诊：能门诊别住院，能住院别进 ICU；所有自动手段用尽才「暴露用户」
- **三级**：① 静默重试（可重试错误：限流/网络抖动——指数退避 + 随机抖动；抖动不是花活，防大量客户端同步醒来形成二次拥塞）② 降级接续（截断续写/换备用模型——本实验不展开，原书实验 5-1/5-2 的重活）③ 暴露用户（附已尝试动作，绝不裸报错）
- **熔断上限**：每条恢复路径都要有上限——Claude Code 压缩重试上限 3 次来自真实事故统计（曾有会话连续失败三千余次，仅此类无效重试日均约 25 万次 API 调用浪费；3 是「绝大多数已恢复」与「继续基本无望」的经验拐点）
- **死亡螺旋**：错误处理路径自身又调 LLM → 再出错 → 连锁（真实形态：上下文溢出 → 停止钩子调 LLM 写 commit message → 又溢出 → 又触发钩子）；防护两条：错误路径禁用一切会再调 LLM 的副作用逻辑 + 递归深度计数器打断连锁
- **实证**：退避序列 0.57s → 0.98s（指数递增 + 抖动，两次运行数字不同）→ 第 3 次成功；持续限流熔断后报错附 3 次尝试记录；bad_stop_hook 以 RecursionError 收场（连锁爆炸的活证据）vs good_stop_hook 一行掐断燃料
- **两层分工**：工具层错误喂回模型（29.2，不终止会话）；API 层错误重试/熔断（29.3，不暴露中间态）——两层各走各路，合起来才是完整的「把错误变成输入」

### 30.1 · 主循环 v1：骨架、规约与三道保险丝
- **比喻**：Agent 运行时 = 事件循环——LLM 是调度器（每轮决定下一个动作）、工具调用是 syscall（进「内核态」干活再返回）、最终文本是进程退出；模型无状态（D09），让它「持续工作」的正是外层循环；Claude Code / Codex 的内核都是它，差异只在循环内外的工程质量
- **工具环规约**：assistant(tool_calls) 与 tool 结果成对追加、append-only——messages 是 WAL 预写日志（D16 回响）：只追加不改历史（改一个字节 = 前缀缓存全灭，D10 回响）；配对是 API 硬约束（D09 铁律、24.2 翻车实证）
- **三道保险丝（循环必须有界）**：轮数上限 / token 预算（usage_metadata 累计）/ 重复指纹（「工具名+参数」连续 3 次相同 → 无进展熔断——29.3 的熔断对象从下游故障换成模型行为；换指纹即重置——连续语义：a,a,x,a,a 不熔断，a,a,a 熔断）
- **轨迹持久化（WAL 正统）**：每条消息产生即落盘 trace.jsonl（先记日志再继续，崩溃后 log 尾部即断点）——中立格式只存 role/content/工具名+参数，不存厂商私有字段（评估重放/跨厂商接管的原料，原书实验 5-1 伏笔）
- **实证**：指纹自检全中；真实任务 4 轮——角色序列严格 append-only 只变长、并行工具调用自然发生（轮 1 双 glob、轮 2 双 read）；trace 9 行 = 9 条轮内新增；彩蛋：WAL 产生即写让 trace.jsonl 出现在 agent 自己的视野里，模型读了它并正确识别「本次会话自身的记录」——轨迹自指
- **首跑翻车记（两条）**：① bash 的 dir 输出 GBK 乱码——PYTHONIOENCODING 只管 Python 子进程管不住 cmd 内建命令，白名单收窄到 {python}，文件清单职责归 glob_search（语义更专且编码可控）；② DeepSeek 503 过载直接崩（max_retries=0）——29.3 伏笔回收：max_retries=3 打开 SDK 内置指数退避，一级恢复接进循环

### 30.2 · 状态栏注入：环境感知与 KV 前缀保卫
- **比喻**：状态栏是 agent 的仪表盘——每轮推理前把环境快照送到模型眼前（cwd/git 分支/未提交变更），省一轮工具往返；但仪表盘数据每轮都在变，装错位置会把整台机器的缓存烧掉
- **注入位置学（核心对照）**：状态写进 system 且每轮更新 = 静态前缀每轮被改 → 缓存全灭；作为普通消息追加尾部 = 历史一个字节不动 → 前缀稳定持续命中——与 24.2 的 schema 注入同一原则两次落地：动态内容一律走尾部追加
- **实测（DeepSeek prompt_cache_hit_tokens，24.2 同款取数）**：A 反模式每轮命中 0（system 一变从第一字节重算）；B 正解第 1 轮 0（首次）、第 2 轮 1408（整个首轮请求全命中）——「注入位置决定缓存形状」的铁证
- **教学简化注**：真实 Claude Code 注入 cwd/git 分支/未提交变更；本工作区非 git 仓库用文件清单+大小代替——大小正好喂给「读最大的」任务（注入价值显性化）；两版模型都仍先工具核实（工具结果比状态栏新鲜）——合理行为，验收看缓存形状不看路径
- **append-only 的代价与红利同在**：B 版历史里多条 <agent_status> 逐轮堆叠（旧状态留着 = token 渐长）——换前缀稳定，这笔账在长会话里才显性

### 31.1 · 持久化终端会话：cd 为什么会丢
- **比喻**：连接池复用 vs 每次查询重建连接——持久终端 = 长连接，每条命令 = 一次查询；D30 的 bash 每次新 shell = 每次重建连接（cd/venv/env 全蒸发）
- **实现三难点**：哨兵定界（命令后 echo 唯一标记，读到即结束——生产同款思路）/ Windows 管道无 select（读 stdout 阻塞，只能线程看门管超时）/ 长输出头尾截断（头 15 + 尾 5 中间省略——D25 回响）
- **实证**：A 无状态 cd 白做（回到起点）；B 常驻 cmd：cd sub → cd 显示 \.sub、dir /b 列出 note.txt（cwd 真跟走了）、set NOTE → echo %NOTE% = hello；40 行输出截成 15 + 省略 20 + 5
- **首跑翻车记（cmd 分隔符三大坑，一个比一个阴）**：① & 连接哨兵会被 for 吃进循环体——每轮都输出 tag，reader 第一轮就停（40 行只出 1 行）；② 括号分组隔离 cd——(cd sub) 块结束目录被还原（set 不受影响）；③ \r\n 的 \r 粘进命令尾部——cd sub\r 找不到目录；终解：哨兵独立成行 + 纯 \n 换行
- **简化注**：cmd 内建命令 GBK 自洽，python 命令混编码勿混用；超时只返回不重建（真实系统杀进程重建会话）

### 31.2 · 行号漂移陷阱：编辑为什么收敛到内容匹配
- **比喻**：行号是外部状态（模型看不见应用后的坐标漂移）；内容就在上下文里（看得见、对得上）——业界从抽象定位（行号/Vim）收敛到内容匹配（old→new/首尾匹配）不是品味，是数学
- **五方案定位**：diff+Apply Model（主模型省 token 但合并环节脆）/ old→new（唯一即成功、失败明确可自纠——Claude Code、Codex、Cursor 现行共同选择）/ 行号（大段删除只需两个数字但漂移陷阱）/ 类 Vim（为人「边看边改」设计，模型「长思考一次批量输出」工作模式根本不同）/ 首尾匹配（old 的改进：只给开头结尾几行，兼顾可靠与省 token）
- **实证**：同一文件两处同型修改——A 行号方案：第二处按快照行号（漂移 +1）静默删错（enrich 消失 + 不可达双 return——真实事故就是这种歪歪扭扭的错法）；**compile 通过（静默！）运行 NameError 才炸**——「compile 过了 ≠ 改对了」三层证据链（read 看得见 / compile 不报 / run 才炸）；B old→new：两处独立匹配全成功（即时语法检查内嵌）
- **B 版代价注**：old_string 要完整输出原文（含上下文）——大段删除时费 token；首尾匹配方案优化的正是这个

### 31 · 服务端真值校验（概念卡，未落实验）
- **核心**：涉及业务规则的操作，所有事实必须服务端查库获得（订单状态/归属/退款金额），模型自报参数只当参考——防线建立在模型无法伪造的数据之上（模型可能幻觉，也可能被提示注入操纵——D12/D26 回响）
- **后端类比**：客户端参数仅作 UI 提示，服务端权限校验必须查库——后端安全基本功在 Agent 工具设计里同样成立
- **自报值的正确用法**：不一致告警——模型自报与库中真值不符 = 幻觉或注入的信号（检测层回响）
- **思考题答案（取消订单）**：必须查库——订单当前状态（已发货就不能取消）、订单归属（是不是这个用户的——越权防线）、退款金额（按实付算不能信模型报数）；可自报——订单号（作为查询 key 但要校验归属）、取消原因文案（展示性内容）

### 32.1 · 网络出口控制：掐断攻击链的收益端
- **比喻**：三要素 ≈ 同时拥有「数据库读权限 + 用户任意输入 + 公网出网」却没有 WAF 和出口防火墙——任何一环缺失攻击链就断；掐断出口 = 掐断攻击收益（与数据库最小权限同构：不是防住所有注入，而是让注入拿不到东西）
- **致命三要素（Simon Willison）**：①访问私有数据 ②暴露于不受信内容 ③外部通信能力——单独都正常，齐备成灾；原书补第四维：**持久记忆是放大器**（恶意指令写进 MEMORY.md 跨会话潜伏择机触发——写入记忆的内容要过与外部内容同等的信任审查）
- **实证（egress 攻击演练）**：pypi.org.evil.com（子域名仿冒）与 pypi.org@evil.com（userinfo 仿冒）——「字符串 contains」实现全被骗放行；urlparse 解析 hostname 后全等比对全拒绝（@ 前是 userinfo 真 host 在 @ 后；hostname 自动小写——Pypi.Org 放行）；IP 直连同样拒绝
- **凭证隔离**：路径锁拒绝 ../ 逃逸（两条变体全拒）；生产更强——凭证根本不挂载进沙盒（容器不 volume ~/.ssh），**读不到的文件不需要防御，挂载层即信任边界**
- **作业③答案（三要素盘点）**：我们的玩具 Agent——①是（read_file 全工作区）②弱（无抓取工具但任务文本不可信）③是（py_exec 可 requests 任意 URL）→ 砍第③条：默认断网 + 白名单代理
- **简化注**：egress 是纯函数判定演示；接进 py_exec 需在代理层拦 requests/urllib 出口

### 32.2 · 沙箱执行：结构化超时反馈
- **比喻**：「杀掉就完事」与「死得明白」的区别——超时反馈带死前最后输出，模型下一轮看得到它被杀前干了什么（打印到第几次心跳）才能修正策略；静默失败 = 模型只能瞎猜（D25/D29 在超时场景的合流）
- **实证**：while True 心跳死循环——3s 短超时拿到「心跳 5」；集成路径 bash 跑 spin.py 15s 绳生效，返回「[超时] 超过 15s 被终止。最后输出：心跳 0..30」全量 31 条——对照升级前的一句话反馈，多出来的就是模型修正策略的唯一新信息
- **首跑翻车记（两层，都修进 common）**：① 死前输出空——管道下子进程 stdout 块缓冲，几条心跳填不满缓冲区、被杀时没 flush——修复：env 强制 PYTHONUNBUFFERED=1（框架层统一，不能指望子进程自觉 -u）；② bash 挂死——subprocess.run(shell=True) 超时只杀 cmd 外壳，**孙进程成孤儿持有管道写端，收尾读永久阻塞**——修复：taskkill /F /T 级联杀进程树后再读
- **限额跨平台形态（注释级）**：Unix preexec_fn + resource（RLIMIT_CPU/RLIMIT_AS）；Windows Job Object；容器 --memory/--cpus（26.2 实测 OOM Killed）——死循环吃 CPU 绳先杀；内存炸弹/fork 炸弹/无限写盘各对应限额

### 32.3 · 命令安全：语义解析而非关键字黑名单
- **比喻**：黑名单/手写规则匹配的是「字符」，LLM 审查理解的是「意图」——SQL 参数化查询 vs 字符串拼接过滤（后者永远堵不完）；第一章「基于理解而非匹配」在命令层的落地
- **三层对照（「匹配」的两个尽头与「理解」本身）**：A 黑名单（首命令字符串）→ B 手写规则（课件伪代码直译——懂 find -exec / curl -o / $() 三条消费规则）→ C LLM 语义审查（**生产路线：Claude Code/Codex 的 bash 权限检查就是 LLM 分类器**，26.3 Sidecar 同款）
- **实证（六案例三列）**：课件三攻击 A 全放行、B 全拦；**换壳两攻击（bash -c "rm -rf"、python -c os.system）A/B 全放行**——规则表里没有这两种壳，「匹配」的尽头当场实证；C 全拦且 reason 精准（「展开后实际执行 rm -rf /」「通过 Python 调用 Windows del」）；无害命令 C 放行（「不会执行下载内容」）
- **教训（首版翻车，用户退回）**：首版把课件伪代码直译的手写规则放在解法侧自我标榜「语义解析」——换壳即绕过，与黑名单同宗只是规则更长；解法侧必须对齐生产（LLM 审查），手写规则降级为中间对照组——它拦得住课件例子恰恰是陷阱：**过课件 ≠ 生产可用**
- **与生产的差距（注明）**：真实 Claude Code 用长驻小模型与主模型并行（数百毫秒无感）；本实验同步调用主模型；LLM 审查非 100% 可靠，生产与白名单/沙箱叠成纵深防御 + 只喂结构化字段防注入带偏审查员（26.3）

### 33 · 元能力：代码 = 能创造其他能力的能力
- **比喻**：普通能力像已部署的微服务接口，元能力像平台的动态插件机制——需求来了现场编译加载新 handler，不等下个版本排期；六层同心圆由内向外（思维→规则→呈现→接口→UI→自举），不是平行罗列——越向外，代码改造的对象越接近 Agent 生态本身
- **模型与脚手架此消彼长**：模型够强时脚手架可以更薄（纯思考算得对，代码增益收窄）；模型弱时关键推理必须交给代码——**评估任何 Agent 技术都要带上前提**：同一套脚手架配不同能力的模型，结论可能截然相反
- **LLM+代码分工（①层）**：LLM 理解开放表达 → 翻译成 SymPy/约束求解器代码 → 解释器精确计算（Wolfram 符号计算保持 √2 精确形式但自然语言理解脆弱，恰好互补）；D6 ReAct 已是此形态
- **Artifact 模式（④层延伸）**：Agent 只生成 SQL/可视化代码作为可执行产物，数据从库直达前端，**LLM 完全不碰数据**（执行+读几千行+文字复述 = 慢、贵、抄写必错）；前提：只读账号、只放 SELECT、参数化绑定、限行数限超时
- **生成式 UI（⑤层）**：A2UI 声明式——Agent 只输出 JSON 界面清单，客户端用受信任组件目录渲染（「只能点菜，不能进厨房」；直接生成 HTML 的风险是注入≈XSS）；**权限下沉**：目标不是 AI 每次写对权限，而是写错了也绕不过——信任边界下移到数据层（行级安全/约束/受控视图），应用层预检查只为体验，数据层保留最终裁决权
- **PPT 双 Agent（③层）**：Proposer 生成 + Reviewer 渲染成图 + Vision 结构化建议（页码/问题类型/严重度）+ 显式终止条件；双 Agent 的核心优势是**上下文管理**（Reviewer 每次只看最新渲染图，单 Agent 堆几十页图多轮迭代很快爆掉）；差距注：deepseek-chat 无视觉能力，本仓库只做了 D4/D5 文本互审骨架
- **Agent 自举（⑥层）**：OpenClaw doctor 两层——确定性检查覆盖高频问题（token 过期/锁文件/端口冲突）+ LLM 兜底长尾；创造新 Agent 的最有效技巧：基于高质量范例修改（范例代码本身就是最佳实践载体）

### 33.1 · 自写工具并注册：生成→验证→注册→使用（作业①②③落点）
- **闭环四步**：①生成（SPEC 签名+用例要求 → LLM 写函数）→ ②沙箱验证（subprocess 隔离+绳，失败报告结构化：用例名/got/error）→ ③失败带报错重写一次（D29.2 测试-修复循环复用）→ ④wrap 成 StructuredTool 注册
- **自举目标选 extract_json 的理由**：32.3 的 llm_scan 刚手写 re.search 剥 ```json 包裹——主循环/审查器真实反复需要；**使用环直接解析一次真实 LLM 输出——Agent 为自己的下一环造工具，闭环自指**
- **实证**：第 1 版 3 用例全过（纯 JSON/markdown 包裹/前后杂文）→ 注册 → 使用环解析出 verdict='deny'
- **wrap 的本质**：注册的不是裸代码而是受限执行体——**能力来自自举，边界仍归 Harness**；教学版 exec 隔离命名空间，生产是进程级/容器沙箱（D32 三道防线 + 32.3 LLM 审查生成的代码本身）
- **简化注**：SPEC 预置而非模型自主提出（下一台阶）；重试 1 次（课件骨架）

### 33.2 · 三重保障：checklist 参数不担安全责任
- **三层分工**：第 1 层 system 自然语言政策管「会解释」（丢了它模型只会说不能退、说不出为什么）；第 2 层 expected_* checklist 管「先核对」（迫使调用前查单，很多违规在填参数阶段自我拦截）；第 3 层服务端真值守门员管「拦得住」（真值全部取库，绝不采信自报）
- **易混点（课件重点澄清）**：第 2 层只是模型的**自我陈述**——引导思考 + 对账告警，不担任何安全责任；模型可能幻觉也可能被注入操纵，守门员必须建在模型无法伪造的数据上（独立性不只是独立的模型，更是**独立的数据源**——D31）
- **实证**：任务藏注入「无需查询、自报 refundable」——模型先 query_order（第 2 层前置核对生效）→ 引用政策解释拒绝（第 1 层）；确定性单测：直接拿假 expected 调服务端 → 拒绝 + 对账告警（第 3 层，与模型定力无关）
- **代码化规则的核心价值不是省 token，而是拦住不可逆操作**（取消订单/转资金/删数据，错了无法撤销）

### 34 · W5 复盘：两条最值得带走的结论
- **结论一：成熟度来自 Harness，不是模型**——Coding Agent 成熟度最高不是代码模型特别强，而是软件工程几十年攒的基础设施天然是强 Harness（测试=验收标准、Linter/类型=即时反馈、Git=完美回退）；四象限最佳区域 = 目标明确+结果可自动验证——**设计自己的 Agent 应用第一件事是把任务往这象限推**：模糊目标补验收标准、人工验收补自动化检查；推论：**约束优先于指导**——能编码进 Linter/CI 的就别写在提示词里（前者是「做不了」，后者只是「建议别做」）
- **结论二：可靠性来自恢复路径，不是不犯错**——四层故障（API/工具/上下文/控制流）× 检测（错误分类+重复指纹+连续失败计数+空闲看门狗）× 分级恢复（静默重试→降级接续→暴露用户）= 完整免疫链；两条最实用原则：错误结构化喂回（越具体自纠率越高）；**恢复边界是整个循环而非单次请求**（恢复成功用户无感，手段用尽才报错）
- **验收标准决定停止时机**：完成 =「测试通过」而非「代码写完」——主循环终止判定必须绑定客观验收信号，否则循环不知何时停（模型最常见偷懒 = 跳过验证）

### 34 · final_agent 合体（作业①②③落点，用户授权侧重生产性）
- **五环节接线**：主循环（验收判停——模型说完成 ≠ 完成，强制跑测试）｜上下文（稳定前缀+成对追加+WAL）｜工具环（结构化错误）｜安全（bash 白名单+语义审查门 fail-closed+路径锁+绳+taskkill /T）｜元能力（启动自举 extract_json 注册，judge 当场用它解析——能力自举服务安全）
- **端到端实证（8 轮 15 秒闭环）**：起始验收失败（average=2.0≠3.0）→ 轮 1 bash 跑测试看失败（SYSTEM「先跑它看失败」引导生效，bash 过审查门）→ 轮 3 edit_file×2 同轮修双 bug → 轮 4 复跑仍挂 → 轮 6 补修 → 轮 7 复跑 → 声明完成 → acceptance 强制验收「通过：3/3」——理解→改代码→执行→验证→汇报全链路
- **两个生产细节（D34 真正的新增量）**：① **验收资产由 Harness 持有**——acceptance 每次重写 test_stats.py 再跑，模型篡改测试作弊的路径物理切断（D31「守门员建在模型够不着的真值上」延伸到验收信号）② repair 循环 = 课件 run_task 伪代码：solve → 验收不过 → 失败报告喂回 → 再修（保险丝兜底：轮数 12/指纹连续 3 次）
- **最薄弱一环（作业②，诚实记录）**：审查门只挂 bash——py_exec 代码、write_file/edit_file 落盘内容同样可藏恶意动作；生产应全执行路径过审 + 源码只读挂载补丁流（D32 防线二的完整形态）
- **思考题 1 答案（作业③）**：安全与能力的平衡 = 分场景配置而非全局开关——日常代码任务默认断网+源码只读；联网装依赖走出口白名单按需放行（32.1）；凭证操作永不进沙盒（挂载层即信任边界）——平衡点是**按任务动态收缩的权限边界**
- **长度说明**：收官合体 ~180 行，用户授权「复盘综合性内容可牺牲教学性侧重生产性」——超教学红线在案

### 35 · 调试第一性原理与五类体检（W5 项目检查点）
- **第一性原理**：模型只对它看到的上下文负责——普通程序调试怀疑逻辑，Agent 调试先怀疑上下文；定位行为异常的第一步不是改提示词，而是把当时的完整 messages 打出来看（「模型太笨」多半是「模型根本没看到」）；推论：任何没进入上下文的事实，对模型就不存在
- **五类高频 bug 与修法**：①主循环无终止→显式判停+最大轮数兑底；②工具结果没喂回→成对 append-only（对第一性原理最直接的违反）；③old_string 失配→透明报错+真实片段喂回让模型自纠（不是你替它改——D31 设计特性）；④超时静默→结构化错误带回死前输出（D32）；⑤自写工具没校验→动态注册走和内置工具同一套校验管道（D33）
- **体检结论（v2 实测）**：命中 0/5 完全缺陷、1/5 部分差距（注册工具未过审查管道——judge 只挂 bash）；四类全过不是运气，是 D30-D33 每天补的课
- **轨迹回放**：后端 trace 的 Agent 对应物——每轮完整 messages/工具调用/结果/耗时落 JSONL，出问题逐轮回放；「玄学问题」在轨迹里一目了然（第 3 轮调错参数，根源常在第 2 轮工具返回了截断的 JSON）；10 行投入换之后所有调试效率的指数提升，也是 W7 可观测性评估的地基

### 35.1/35.2 · mini Coding Agent v2（作业①②③落点）
- **v2 相对 D34 的升级**（回应「D34 还不算 Coding Agent」）：①任务从「修 2 个预置 bug」升级为「从需求从零实现模块」（word_freq/top_k——理解→设计→实现→自测→汇报，六阶段微缩走全）②轨迹从简版 WAL（截 300 字、漏 assistant 文本）升级为完整事件流（ts/turn/kind/content 不截断）

- **长度说明**：~230/~90 行，延续 D34 用户授权（复盘综合性内容侧重生产性）

## 自测（遮住括号自测）

1. 为什么通用 Agent 的核心是 Coding Agent 而不是 Deep Research 或 Computer Use？（几乎所有高效内容生成都落到代码上——OOXML/Markdown→PDF/pandas/代码驱动抓取；Computer Use 成本/延迟/稳定性全不如直接写代码调 API——代码是效率最高、成本最低、可复用性最强的能力基座）
2. 这个论断的适用边界？（开放任务（产物形态多样）；客服这类任务空间封闭的产品核心仍是固定业务流程，代码只是工具箱一员）
3. 七件套是哪七件？为什么理论上一个 bash 就够还要拆七件？（py_exec/bash/read/write/edit/glob/grep；OpenAI Codex 只给 bash——拆开让调用更精准，模型说「找文件」直接 glob 不用 bash dir 再解析；D24 回响：描述清楚比数量少更重要）
4. 七件套落在五分类的哪两轴？（感知三件 read/glob/grep + 执行四件 write/edit/bash/py_exec；协作/事件触发/用户沟通不是 Coding Agent 的核心）
5. OpenClaw 为什么用 MEMORY.md 而不是向量库做长期记忆？（用户能直接打开修改（记错删一行）、天然保留时间顺序、可走 Git 版本控制和回滚——可审计可回滚的 git 仓库而非黑盒数据库）
6. 工程化六阶段是哪六步？哪一步是人类最佳介入点？（项目文档化→需求澄清→设计文档→实现+测试→自我审查→文档同步；设计文档——审查一份文档远比审查几百行代码容易）
7. 「测试通过」和「代码写完」哪个是完成标准？为什么？（测试通过——Coding Agent 最常见的偷懒就是写完不跑测试就报告完成；29.2 的终检以落盘测试为准不以模型自评为准）
8. Harness 四件套？（验收基线（什么算做完——测试/CI）/ 执行边界（能碰什么——权限）/ 反馈信号（自动对错——lint/测试）/ 回退手段（怎么恢复——git/沙盒/快照））
9. 「目标清晰度 × 验证自动化」四象限，代码任务在哪个象限？为什么？（最佳象限：目标明确 + 结果可自动验证——测试套件给验收标准、lint/类型检查给即时反馈、git 给回退；Coding Agent 成熟度最高是基础设施的功劳，不是模型特别强）
10. 约束优先于指导是什么意思？约束的第二层目的？（能 Linter/CI 强制的别写提示词请求——「做不了」远强于「建议别做」；防过程性错误：删库重建结果对过程是灾难，rm -rf 拦的是动作而非仅仅结果）
11. API 层三级恢复按什么排序？每级干什么？（对用户透明度：静默重试（指数退避+抖动）→ 降级接续（截断续写/备用模型）→ 暴露用户（附已尝试动作）——能用低级别解决就不升级）
12. 抖动（jitter）解决什么问题？熔断上限的 3 从哪来？（大量客户端同步退避再同步醒来形成二次拥塞；Claude Code 压缩重试 3 次——真实事故统计里曾有会话连续失败 3000+ 次，3 是经验拐点）
13. 工具层错误和 API 层错误为什么走不同的路？（工具层不终止会话：结构化错误喂回模型下一轮自纠（反馈越结构化越好）；API 层重试/熔断不暴露中间态——两层合起来才是完整的「把错误变成输入」）
14. 死亡螺旋怎么防？（错误路径上禁用一切会再调 LLM 的副作用逻辑（宁丢辅助功能不做连锁燃料）+ 递归深度计数器打断残余连锁——29.3 的 RecursionError 是活证据）
15. 主循环的事件循环类比里，LLM/工具调用/最终文本各对应什么？（调度器/syscall/进程退出；模型无状态，外层循环在维护状态、执行动作、喂回结果）
16. 「每轮重新拼 prompt」的误区，正确姿势是什么？（维护持久化 messages 列表只追加——前缀稳定缓存才命中，轨迹天然可持久化可恢复）
17. 一次工具调用在 messages 里占几条？什么规约？（两条：assistant(tool_calls) + tool 结果；成对出现、按序追加、不改历史——WAL 预写日志）
18. 工具报错为什么不能 break 退出循环？（错误作为普通 tool 结果喂回，模型下一轮自纠——反馈越结构化自纠率越高；29.2/30.1 同款规约）
19. 三道保险丝各拦什么？重复指纹的「连续」语义？（轮数防死循环总闸、token 预算防烧钱、指纹防无进展循环；换指纹即重置——a,a,x,a,a 不熔断，a,a,a 熔断）
20. 状态栏为什么不能写进 system？（状态每轮在变——写 system = 前缀每轮被改 = 缓存全灭；实测 A 版每轮命中 0，B 版第 2 轮 1408）
21. 轨迹为什么「产生即落盘」而不是轮末统一写？（轮末写入会被提前 return 跳过——30.1 首跑最终回答漏盘的教训；WAL 正统：崩溃后 log 尾部即断点）
22. 中立轨迹格式存什么不存什么？（role/content/工具名+参数；不存厂商私有字段（凭证/ID）——评估重放与跨厂商接管的原料）
23. 文件编辑的核心张力？（LLM 高效可靠地告诉系统「改哪里怎么改」——人类语言表达 vs 机器精确执行；定位越精确容错越差，越模糊成功率越低——方案是在两者间找平衡）
24. 五种编辑方案中业界收敛到哪个方向？为什么？（内容匹配（old→new/首尾）——内容就在上下文里看得见对得上；行号是外部状态，模型算不准漂移后的坐标）
25. 行号漂移陷阱怎么发生？解法？（模型基于阅读时行号快照提交多处编辑，框架逐个应用——第一处完成后行号集体漂移，后续按旧行号静默错位；解法：像 diff 一样统一用初始行号由框架算偏移，或干脆用内容匹配）
26. 「compile 过了」等于「改对了」吗？（不——31.2 实证：行号错位删掉 enrich 调用后语法依然合法，运行才 NameError；完成标准必须是「测试通过」（29.2）而非「代码写完」的又一证据）
27. 为什么需要持久化 shell？（cd/venv/env/后台服务都是会话状态——每次新 shell 全丢；类比连接池复用 vs 每次重建连接）
28. cmd 分隔符三大坑（31.1 首跑翻车）？（& 被吃进 for 循环体、括号分组隔离 cd、\r 粘进命令尾部——哨兵独立成行 + 纯 \n 换行终解）
29. 服务端真值校验的核心主张？（业务规则操作的事实必须服务端查库（状态/归属/金额），模型自报只当参考 + 不一致告警——防线建立在模型无法伪造的数据上）
30. 取消订单哪些参数必须查库？哪些可让模型自报？（状态/归属/退款金额——决定动作合法性与结果数值的；订单号可自报但要校验归属，取消原因文案可自报）
31. 致命三要素是哪三条？为什么单独正常、齐备成灾？（访问私有数据 × 暴露于不受信内容 × 外部通信能力；攻击链闭合：恶意指令进来 → 读私密 → 传出去——后端类比 DB 读权限 + 任意输入 + 公网出网无 WAF）
32. 原书补充的第四维度是什么？（持久记忆是放大器——恶意指令写进长期记忆跨会话潜伏择机触发；写入记忆的内容要过与外部内容同等的信任审查）
33. 网络出口控制为什么是第一道防线？（回看三要素③——即使注入成功、沙盒里读到了敏感数据，没有出口就传不出去；掐断通道 = 掐断收益，与数据库最小权限同构）
34. egress 白名单实现的经典翻车点？（子域名仿冒 pypi.org.evil.com 与 userinfo 仿冒 pypi.org@evil.com 骗过字符串 contains；正解：urlparse 解析出真 hostname（自动小写）全等比对）
35. 超时后为什么要返回结构化错误而非静默杀？（带死前最后输出——模型下一轮看得到被杀前干了什么才能修正策略；静默失败 = 模型只能瞎猜）
36. 32.2 首跑的两层翻车？（① 子进程 stdout 块缓冲——死前输出没 flush 进管道，修复 PYTHONUNBUFFERED=1；② shell=True 超时只杀 cmd、孙进程孤儿持管道写端收尾挂死——修复 taskkill /T 级联杀）
37. 命令语义解析的生产主流形态？为什么手写规则不行？（LLM 审查器——Claude Code/Codex 的 bash 权限检查、26.3 Sidecar 同款；手写规则换壳即失效：bash -c "rm -rf" / python -c os.system 首命令「干净」——规则表永远追着攻击跑，过课件例子 ≠ 生产可用）
38. 黑名单为什么永远堵不完？LLM 审查怎么破、又该怎么用？（Shell 组合爆炸——管道/子 shell/变量展开/命令替换换着花样藏动作；LLM 不枚举规则直接看「它实际会做什么」——但非 100% 可靠，生产与白名单/沙箱叠纵深 + 只喂结构化字段防注入带偏审查员（26.3））
39. 元能力是什么？六层同心圆由内向外？（能创造其他能力的能力；思维→业务规则→内容呈现→系统接口→用户界面→Agent 自身——不是平行罗列，越向外越接近 Agent 生态本身）
40. 模型与脚手架此消彼长指什么？（模型强→脚手架薄、代码增益收窄；模型弱→关键推理交代码——评估要带前提：同套脚手架配不同模型结论截然相反）
41. 自写工具闭环四步？（生成 → 沙箱用例验证 → 失败带报错重写 → wrap 注册受限执行体——能力来自自举，边界仍归 Harness）
42. wrap 注册为什么不是裸代码？（沙箱包装后的受限执行体：进程级隔离/限额/审查；教学版 exec 隔离命名空间是简化——注差距）
43. 三重保障各层管什么、谁担安全责任？（①政策提示词管会解释；② expected_* checklist 管先核对（自我陈述）；③服务端真值守门员——只有 ③ 担责任，建在模型无法伪造的数据上）
