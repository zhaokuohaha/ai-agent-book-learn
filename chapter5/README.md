## 记忆卡

### 29 · 全景：为什么核心是 Coding Agent（概念日）
- **比喻**：W1-W4 学的上下文/记忆/工具是器官，今天开始拼完整机体——躯干是 Coding Agent，文件系统是循环系统
- **适用边界**：论断针对开放任务（产物形态多样的调研/生成/数据处理）；客服这类任务空间封闭的产品，核心仍是固定业务流程，代码只是工具箱一员
- **文件系统中枢**：OpenClaw 用 MEMORY.md + 按日期归档 Markdown，故意不用向量库——用户能直接打开改（记错了删一行）、天然保留时间顺序、可走 Git 版本控制回滚（「把状态存进可审计可回滚的 git 仓库，而不是黑盒数据库」）；Agent 能写文件 = 具备沉淀经验、修改自身外部产物的技术前提（持续进化的伏笔，第 9 章）
- **工程化六阶段**：项目文档化 → 需求澄清 → 设计文档 → 实现+测试 → 自我审查 → 文档同步。项目指令文件（CLAUDE.md/AGENTS.md）= 项目级系统提示词，会话自动注入、内容稳定，天然 KV Cache 友好前缀（D10/D13 回响）；设计文档是人类最佳介入点——审查一份文档远比审查几百行代码容易；现实按需裁剪（修 bug 直接进实现）
- **Harness 四件套**（W1 公式的 Coding 落地）：验收基线（什么算做完——测试/CI）/ 执行边界（能碰什么——权限/模块边界）/ 反馈信号（自动对错——lint/测试）/ 回退手段（怎么恢复——git/沙盒/快照）。「目标清晰度 × 验证自动化」四象限里代码任务天然在最佳象限——Coding Agent 成熟度最高不是模型特别强，是软件工程几十年的基础设施天然构成强 Harness
- **约束优先于指导**：能 Linter/CI 强制的规则就别写在提示词里请求（「做不了」远强于「建议别做」）；第二层目的是防过程性错误——删库重建「结果对了过程是灾难」，rm -rf 这类危险动作要专门拦截，约束的是动作而非仅仅结果（D26 执行边界回响）

### 29.1 · 七件套：通用 Agent 的全套手脚
- **比喻**：D28 的 3 工具配齐到 7 件——一个最小文件系统 API + 受限 shell，承载几乎所有任务
- **为什么七个不是八个**：理论上一个 bash 就够（OpenAI Codex 就这么干），拆七件让调用更精准——模型说「找文件」直接 glob，不用 bash dir 再解析输出（D24 回响：七个远够不到规模门槛，描述清楚比数量少更重要）
- **五分类落位**：感知三件（read/glob/grep）+ 执行四件（write/edit/bash/py_exec）；协作/事件触发/用户沟通不是 Coding Agent 的核心（第 6 章）
- **伴生三技巧**：行号标注读（「4→code」精确引用行号，后续 edit 更可靠）/ old→new 精确编辑（Claude Code/Codex/Cursor 现行方案：唯一即成功、不唯一或找不到即报错，绝不模糊匹配——22.4 参数保真回响）/ 写后即时语法检查（py_compile——IDE 红线思维，错误在引入当刻可见）
- **实证**：grep 定位 TODO → read 带行号 → edit 修分母 bug → edit 消歧失败（"return" 出现 2 次不改文件）→ write 缺括号当场 SyntaxError → py_exec 验证 average([2,4])=3.0（修复铁证）。实现沉淀 common/coding_tools.py（make_tools(ws) 工厂闭包绑定工作区，29.2 与 D30 复用——common/memory_store.py 先例）

### 29.2 · 测试-修复循环：「测试通过」才算完成
- **比喻**：完成标准从「代码写完」换成「测试通过」——Coding Agent 最常见的偷懒就是不跑测试就报告完成
- **确定性闭环设计**：预置带 bug 的 stats.py + 必失败的 test_stats.py——初始状态确定失败，Agent 必走「跑测试 → 失败输出回填 → 读代码 → edit 修复 → 再跑 → 通过」
- **错误变输入（工具层恢复）**：测试失败输出原样回填 ToolMessage（不终止会话）；幻觉调用收到「工具不存在 + 可用清单」；工具异常同样结构化喂回——「反馈越结构化越好」（与 D26.4 Sidecar 拒绝回执、27.3 HITL 回执三处同构）
- **system 注入（AGENTS.md 微缩，作业②代码落点）**：项目约定（edit_file 局部修改、测试通过才算完）进 system、任务指令精简为两句——任务文本不再提「用 edit_file」，模型仍走 read → edit → bash 测过的路径：约定从 system 生效（D11 信任分层：项目级约定 vs 任务级指令；D10 稳定前缀回响）
- **实证**：三次运行轨迹各异（先 bash 撞失败→修复 / 先 read 探查；system 版直接 read→edit→测过）但闭环结构一致；模型曾自发用 py_exec 加测边界（空序列抛 ValueError）——超纲的自觉；终检以落盘测试为准，不以模型自评为准
- **首跑翻车记**：终检 subprocess 漏设 PYTHONIOENCODING——agent 轨迹里 bash 返回正常「全部测试通过」，终检却 GBK 乱码误判「仍失败」；子进程读中文必须带编码环境变量（与 bash 工具同款处理）

### 29.3 · 故障恢复：分级升级、熔断与死亡螺旋
- **比喻**：恢复手段按对用户透明度分级——像急诊分诊：能门诊别住院，能住院别进 ICU；所有自动手段用尽才「暴露用户」
- **三级**：① 静默重试（可重试错误：限流/网络抖动——指数退避 + 随机抖动；抖动不是花活，防大量客户端同步醒来形成二次拥塞）② 降级接续（截断续写/换备用模型——本实验不展开，原书实验 5-1/5-2 的重活）③ 暴露用户（附已尝试动作，绝不裸报错）
- **熔断上限**：每条恢复路径都要有上限——Claude Code 压缩重试上限 3 次来自真实事故统计（曾有会话连续失败三千余次，仅此类无效重试日均约 25 万次 API 调用浪费；3 是「绝大多数已恢复」与「继续基本无望」的经验拐点）
- **死亡螺旋**：错误处理路径自身又调 LLM → 再出错 → 连锁（真实形态：上下文溢出 → 停止钩子调 LLM 写 commit message → 又溢出 → 又触发钩子）；防护两条：错误路径禁用一切会再调 LLM 的副作用逻辑 + 递归深度计数器打断连锁
- **实证**：退避序列 0.57s → 0.98s（指数递增 + 抖动，两次运行数字不同）→ 第 3 次成功；持续限流熔断后报错附 3 次尝试记录；bad_stop_hook 以 RecursionError 收场（连锁爆炸的活证据）vs good_stop_hook 一行掐断燃料
- **两层分工**：工具层错误喂回模型（29.2，不终止会话）；API 层错误重试/熔断（29.3，不暴露中间态）——两层各走各路，合起来才是完整的「把错误变成输入」

### 30.1 · 主循环 v1：骨架、规约与三道保险丝
- **比喻**：Agent 运行时 = 事件循环——LLM 是调度器（每轮决定下一个动作）、工具调用是 syscall（进「内核态」干活再返回）、最终文本是进程退出；模型无状态（D09），让它「持续工作」的正是外层循环；Claude Code / Codex 的内核都是它，差异只在循环内外的工程质量
- **工具环规约**：assistant(tool_calls) 与 tool 结果成对追加、append-only——messages 是 WAL 预写日志（D16 回响）：只追加不改历史（改一个字节 = 前缀缓存全灭，D10 回响）；配对是 API 硬约束（D09 铁律、24.2 翻车实证）
- **三道保险丝（循环必须有界）**：轮数上限 / token 预算（usage_metadata 累计）/ 重复指纹（「工具名+参数」连续 3 次相同 → 无进展熔断——29.3 的熔断对象从下游故障换成模型行为；换指纹即重置——连续语义：a,a,x,a,a 不熔断，a,a,a 熔断）
- **轨迹持久化（WAL 正统）**：每条消息产生即落盘 trace.jsonl（先记日志再继续，崩溃后 log 尾部即断点）——中立格式只存 role/content/工具名+参数，不存厂商私有字段（评估重放/跨厂商接管的原料，原书实验 5-1 伏笔）
- **实证**：指纹自检全中；真实任务 4 轮——角色序列严格 append-only 只变长、并行工具调用自然发生（轮 1 双 glob、轮 2 双 read）；trace 9 行 = 9 条轮内新增；彩蛋：WAL 产生即写让 trace.jsonl 出现在 agent 自己的视野里，模型读了它并正确识别「本次会话自身的记录」——轨迹自指
- **首跑翻车记（两条）**：① bash 的 dir 输出 GBK 乱码——PYTHONIOENCODING 只管 Python 子进程管不住 cmd 内建命令，白名单收窄到 {python}，文件清单职责归 glob_search（语义更专且编码可控）；② DeepSeek 503 过载直接崩（max_retries=0）——29.3 伏笔回收：max_retries=3 打开 SDK 内置指数退避，一级恢复接进循环

### 30.2 · 状态栏注入：环境感知与 KV 前缀保卫
- **比喻**：状态栏是 agent 的仪表盘——每轮推理前把环境快照送到模型眼前（cwd/git 分支/未提交变更），省一轮工具往返；但仪表盘数据每轮都在变，装错位置会把整台机器的缓存烧掉
- **注入位置学（核心对照）**：状态写进 system 且每轮更新 = 静态前缀每轮被改 → 缓存全灭；作为普通消息追加尾部 = 历史一个字节不动 → 前缀稳定持续命中——与 24.2 的 schema 注入同一原则两次落地：动态内容一律走尾部追加
- **实测（DeepSeek prompt_cache_hit_tokens，24.2 同款取数）**：A 反模式每轮命中 0（system 一变从第一字节重算）；B 正解第 1 轮 0（首次）、第 2 轮 1408（整个首轮请求全命中）——「注入位置决定缓存形状」的铁证
- **教学简化注**：真实 Claude Code 注入 cwd/git 分支/未提交变更；本工作区非 git 仓库用文件清单+大小代替——大小正好喂给「读最大的」任务（注入价值显性化）；两版模型都仍先工具核实（工具结果比状态栏新鲜）——合理行为，验收看缓存形状不看路径
- **append-only 的代价与红利同在**：B 版历史里多条 <agent_status> 逐轮堆叠（旧状态留着 = token 渐长）——换前缀稳定，这笔账在长会话里才显性

### D29 · 作业②（AGENTS.md 五条）参考答案——用四件套组织

1. **验收基线**：新脚本必须实跑验证（空配置友好提示、假 key 到达真实 API 报 401）——什么算做完
2. **执行边界**：配置只走 common/config.py，禁止各章自建配置或直接解析 .env——能碰什么
3. **反馈信号**：模型输出是动态的，验收看执行轨迹（工具是否调用、闭环是否走通），不硬断言固定文案——自动对错怎么判
4. **回退手段**：超长度红线先按砍法取舍序砍演示，砍不动说明概念确实多，拆 NN.M 子实验——出问题怎么恢复
5. **约束优先于指导**：能写进结构强制的（长度红线/命名规则/禁密钥入库）不写成口头建议——「做不了」>「建议别做」

## 自测（遮住括号自测）

1. 为什么通用 Agent 的核心是 Coding Agent 而不是 Deep Research 或 Computer Use？（几乎所有高效内容生成都落到代码上——OOXML/Markdown→PDF/pandas/代码驱动抓取；Computer Use 成本/延迟/稳定性全不如直接写代码调 API——代码是效率最高、成本最低、可复用性最强的能力基座）
2. 这个论断的适用边界？（开放任务（产物形态多样）；客服这类任务空间封闭的产品核心仍是固定业务流程，代码只是工具箱一员）
3. 七件套是哪七件？为什么理论上一个 bash 就够还要拆七件？（py_exec/bash/read/write/edit/glob/grep；OpenAI Codex 只给 bash——拆开让调用更精准，模型说「找文件」直接 glob 不用 bash dir 再解析；D24 回响：描述清楚比数量少更重要）
4. 七件套落在五分类的哪两轴？（感知三件 read/glob/grep + 执行四件 write/edit/bash/py_exec；协作/事件触发/用户沟通不是 Coding Agent 的核心）
5. OpenClaw 为什么用 MEMORY.md 而不是向量库做长期记忆？（用户能直接打开修改（记错删一行）、天然保留时间顺序、可走 Git 版本控制和回滚——可审计可回滚的 git 仓库而非黑盒数据库）
6. 工程化六阶段是哪六步？哪一步是人类最佳介入点？（项目文档化→需求澄清→设计文档→实现+测试→自我审查→文档同步；设计文档——审查一份文档远比审查几百行代码容易）
7. 「测试通过」和「代码写完」哪个是完成标准？为什么？（测试通过——Coding Agent 最常见的偷懒就是写完不跑测试就报告完成；29.2 的终检以落盘测试为准不以模型自评为准）
8. Harness 四件套？（验收基线（什么算做完——测试/CI）/ 执行边界（能碰什么——权限）/ 反馈信号（自动对错——lint/测试）/ 回退手段（怎么恢复——git/沙盒/快照））
9. 「目标清晰度 × 验证自动化」四象限，代码任务在哪个象限？为什么？（最佳象限：目标明确 + 结果可自动验证——测试套件给验收标准、lint/类型检查给即时反馈、git 给回退；Coding Agent 成熟度最高是基础设施的功劳，不是模型特别强）
10. 约束优先于指导是什么意思？约束的第二层目的？（能 Linter/CI 强制的别写提示词请求——「做不了」远强于「建议别做」；防过程性错误：删库重建结果对过程是灾难，rm -rf 拦的是动作而非仅仅结果）
11. API 层三级恢复按什么排序？每级干什么？（对用户透明度：静默重试（指数退避+抖动）→ 降级接续（截断续写/备用模型）→ 暴露用户（附已尝试动作）——能用低级别解决就不升级）
12. 抖动（jitter）解决什么问题？熔断上限的 3 从哪来？（大量客户端同步退避再同步醒来形成二次拥塞；Claude Code 压缩重试 3 次——真实事故统计里曾有会话连续失败 3000+ 次，3 是经验拐点）
13. 工具层错误和 API 层错误为什么走不同的路？（工具层不终止会话：结构化错误喂回模型下一轮自纠（反馈越结构化越好）；API 层重试/熔断不暴露中间态——两层合起来才是完整的「把错误变成输入」）
14. 死亡螺旋怎么防？（错误路径上禁用一切会再调 LLM 的副作用逻辑（宁丢辅助功能不做连锁燃料）+ 递归深度计数器打断残余连锁——29.3 的 RecursionError 是活证据）
15. 主循环的事件循环类比里，LLM/工具调用/最终文本各对应什么？（调度器/syscall/进程退出；模型无状态，外层循环在维护状态、执行动作、喂回结果）
16. 「每轮重新拼 prompt」的误区，正确姿势是什么？（维护持久化 messages 列表只追加——前缀稳定缓存才命中，轨迹天然可持久化可恢复）
17. 一次工具调用在 messages 里占几条？什么规约？（两条：assistant(tool_calls) + tool 结果；成对出现、按序追加、不改历史——WAL 预写日志）
18. 工具报错为什么不能 break 退出循环？（错误作为普通 tool 结果喂回，模型下一轮自纠——反馈越结构化自纠率越高；29.2/30.1 同款规约）
19. 三道保险丝各拦什么？重复指纹的「连续」语义？（轮数防死循环总闸、token 预算防烧钱、指纹防无进展循环；换指纹即重置——a,a,x,a,a 不熔断，a,a,a 熔断）
20. 状态栏为什么不能写进 system？（状态每轮在变——写 system = 前缀每轮被改 = 缓存全灭；实测 A 版每轮命中 0，B 版第 2 轮 1408）
21. 轨迹为什么「产生即落盘」而不是轮末统一写？（轮末写入会被提前 return 跳过——30.1 首跑最终回答漏盘的教训；WAL 正统：崩溃后 log 尾部即断点）
22. 中立轨迹格式存什么不存什么？（role/content/工具名+参数；不存厂商私有字段（凭证/ID）——评估重放与跨厂商接管的原料）
