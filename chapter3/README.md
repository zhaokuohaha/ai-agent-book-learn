## 记忆卡

### 15 · 用户记忆（上）：会话结束，记忆开始
- **比喻**：上下文 = request-scoped 变量（请求结束即释放）；记忆 = 数据库持久层（跨请求存活）；"会话结束 → LLM 提取 → 写入" = 消费会话日志的后台 ETL job
- **提取三规则**：选择性（丢"搜索返回 3 个选项"这类任务脚手架）/ 抽象化（本次"要靠窗" → 长期偏好）/ 结构化（可检索字段，不是流水账）
- **三层次评估**：L1 基础回忆（会员号存取精确）→ L2 多会话检索（两辆车该问哪辆不瞎猜）→ L3 主动服务（订航班发现护照快过期，主动预警——"助理"水准）
- **轨迹 vs 档案**：轨迹 append-only 只增不改（WAL/审计日志）；长期记忆被反复改写、合并、淘汰（ETL 聚合表）——流水账不可变，档案随新事实演进
- **冲突处理取舍（作业 1）**：update 保留旧值带时间戳进 history——时间推理需要（"以前住哪"）、审计回滚需要（LLM 提取可能提错）；代价是存储渐长，生产可归档冷存。delete 用软删除：可恢复 + "曾要求删除"本身也是应被尊重的事实
- **实证**：靠窗→晕机改过道的冲突对话，提取器以最新为准且 history 留下"靠窗（截至 2026-09-24）"；L3 实测模型主动预警"护照 10-05 过期 < 航班 10-20，先换护照再出票"
- **存储格式谱系（D16 展开）**：Simple Notes（一条一事实 O(1)，关联丢失）→ Enhanced Notes（整段叙述语义全，更新难）→ JSON Cards（三层嵌套可部分更新）→ Advanced JSON Cards（backstory/person/relationship 消歧"张医生是谁的医生"）；生产混合：关键少量用高级，大量非关键用 Simple

### 16 · 用户记忆（下）：三分类、仅追加与跨会话 MemoryStore（16.1 主实验 + 16.2 选做）
- **比喻**：情景记忆 = 操作日志（某次订了东京航班）、语义记忆 = 配置表（素食者/靠窗）、程序记忆 = SOP 脚本（搜直飞→确认座位→用常旅客号）；三分类答"存什么"，与层次（存哪里）、格式（怎么存）正交，可自由组合
- **User as Code**：四种格式全是文本，聚合/冲突检测全靠 LLM"心算"不可靠——把记忆改成带类型对象（MemoryEntry）+ 普通函数规则（active() 同 key 取最新），再借 WAL+检查点：remember 只追加（先记日志保证据），load 重放重建状态。能确定性计算的，别让模型算
- **Mem0 v2→v3**：v2 写入时让 LLM 在 ADD/UPDATE/DELETE/NOOP 四选一（库干净但一次误删不可逆）→ v3 仅追加 + 检索时排序（住北京、搬上海两条带时间戳并存，按语义+BM25+实体+时间取当前事实，LoCoMo 71.4→92.5）；Memobase 另一条路：画像槽位精确可控 + 事件时间线 + 攒批提取摊成本——框架只覆盖设计空间一角，按业务取舍
- **第三框架 Supermemory**：不是记忆层是记忆引擎全家桶（提取+画像 static/dynamic≈三分类产品化+hybrid search RAG与记忆一查询+connectors+自动遗忘）；MIT、30k+ stars、local 单二进制可全离线（本地 bge embedding 免 key，接任意 OpenAI 兼容端点）——接入最快、黑盒也最深
- **实证**：session1/session2 两个进程真重启，load 恢复 4 条；靠窗→过道覆盖后 JSON 里两条 seat_preference 并存，active 取 09-28 过道、history 完整时间线；16.2 对照实验：无记忆组反问"请问您想查哪个城市"，有记忆组直接 get_weather(上海)——验收看工具轨迹不看文案。结构：实现沉淀在 common/memory_store.py（可复用组件，后续章节直接 import），实验脚本 16.1/16.2 各自 ≤75 代码行（长度红线首例：原单文件 207 行拆为三）
- **记忆压缩（钩子）**：累积必爆炸——重要性评分（频率/时间衰减/情感强度/独特性）→ 聚类摘要 → 抽象泛化（情景升维成语义/程序）；重复跑 session2 会遇同值条目堆叠，生产靠压缩治理；隐私底线：日志先脱敏再进系统

### 17 · RAG 基础（上）：分块与向量化
- **比喻**：RAG = 模型能力 × 知识库时效性的拼接器（检索→注入→生成）；稠密嵌入 = 把语义变成几何（高维地图，语义越近向量越近）；BM25 = 书后术语索引页（倒排：字面精确），稠密检索 = 查询向量找最近邻（语义模糊）——两路各有所长，明天 RRF 合并
- **分块两原因**：嵌入模型有长度限制（bge-small-zh 512 token）且多主题压一个向量哪个都不准；检索只注入相关小块，块大 = 无关内容灌窗口稀释注意力
- **块大小权衡**：太小→断头碎片（"收入增长 3%"——哪家公司？），太大→多主题混杂向量稀释；实践起点 256-1024 token、重叠 10%-20%；目标"一块一主题"
- **实证（bge-small-zh-v1.5，512 维）**：①查询"退货要多久到账"命中退款块 0.68 最高——"退货"与"退款"零字面重叠，语义几何铁证；②配送块 0.50 与退货块并列——"要多久"撞上配送的时长讨论（48/72 小时），语义检索的模糊性正是 BM25 能补的合；③固定切分 size 20/60/200 的 top-1 得分 0.70/0.69/0.64 单调跌——块越大越稀释；④size=300 整篇一块时"退货到账"与"会员折扣"命中同一块（区分度消失）
- **剧本翻车记（用真实模型的价值）**：Part 3 原设计用结构感知分块验证"块太大区分度消失"，真实跑出来 False——标题是天然边界，结构感知对 size 免疫，该现象只在固定切分下成立。玩具 embed 永远发现不了这种设计错误
- **BGE 细节**：检索不对称——查询侧加指令前缀"为这个句子生成表示以用于检索相关文章："，文档侧不加；DeepSeek 无 embeddings API，本地 bge 是免费替代（HF_ENDPOINT=hf-mirror.com 镜像下载）
- **作业 3 一句话**：块太小则单块语义不完整（命中断头碎片），太大则多主题混杂向量被稀释（不同问题命中同一块）——在检索粒度与语义完整性间求平衡

### 18 · RAG 基础（下）：双引擎检索与精排流水线（18.1 BM25+RRF / 18.2 重排+闭环 / 18.3 三指标）
- **比喻**：BM25 = 修 TF-IDF 两个坑（k1 词频饱和：实测 tf 1→5→10 得分 1.10→2.11→2.39，10 倍词频只换 57% 涨幅；b 长度归一化）；RRF = 跨币种先比排名（序数可比、基数不可比）；稀疏 = 书后术语索引页（倒排），稠密 = 语义地图
- **双引擎盲区互补（实证）**：「退货要多久到账」稠密三块挤 0.01 分差（"要多久"撞上一切时限块：48/72 小时、30 天），BM25 一刀切开（退货 1.69 vs 配送 0）；镜像「包邮有什么条件」BM25 全 0 瞎排，稠密靠"包邮≈免运费"把配送拉到第二——两路盲区恰是对方强区
- **RRF 真发现**：配送（稠密2+BM25四）与退货（稠密4+BM25二）RRF 得分数学上完全相等（1/62+1/64 对称），开票（双第三 2/63）只差百万分之八——名次之和对"哪路更可信"无感，近并列靠插入顺序裁决：粗粒度投票，为重排埋钩子
- **流水线分工（18.2+18.3 实证闭环）**：实测金标块在 RRF 只列第 3，LLM 重排（逐对打 0-10 分，Cross-Encoder 思想）救回第 1；18.3 量化分工——混合保 recall（1.00 vs BM25 0.83）但 MRR 被稀释（0.81 < 稠密 0.92）：双路召回 → RRF 保 recall → 重排修 top-1，各司其职；生成口诀收口：检索→注入（top 片段进 system+标注来源）→生成。双端复现：确定性输出（指标/得分）两次运行逐位一致，LLM 文案微变但要点与来源标注不变——验收看轨迹不看文案
- **三指标**：recall@k 该找的找到没（RAG 命门：金标没进上下文，LLM 连机会都没有）/ MRR 第一个金标够不够靠前（第 1 名 1 分第 10 名 0.1）/ nDCG 整列表质量（1/log2 折损 + 理想归一）；指标也是回归基线——调参/换模型前后各跑一遍对比
- **中文 BM25 命门（实测）**：分词——jieba 把"开发票"切成一词对不上语料"发票"，全 0 瞎排靠并列顺序撞大运（0.0 分"命中"）：字面匹配连字面都可能对不上
- **思考题答案（作业 ③）**：RRF 抛弃原始得分反而稳健，因为两路得分分布不可比（余弦 0~1 vs BM25 可到几十，量纲/尺度/分布全不同），加权融合要调参且脆弱；排名是两路共同的语言——序数可比、基数不可比，RRF 只用排名就天然免疫量纲问题

### 19 · 结构化索引：从扁平 chunk 到知识建模（19.1 翻车现场 / 19.2 迷你 RAPTOR / 19.3 mini GraphRAG）
- **比喻**：原始日志直接撑报表 → 先建聚合表/物化视图——原始材料入库等于把难题甩给检索和模型；扁平库 = 一堆便签（各说各话），图 = 关系网（顺藤摸瓜）；RAPTOR = OLAP rollup（日/周/月多粒度，看大盘又钻明细）
- **三种翻车（19.1 实证）**：top-k 漏召（10 份档案问比例，实测捞回 3 份**全黑**——白猫连上下文都没进，调大 k 也只是 30/100 与 100/100）；最近邻偏置（护士问资格，军医 Sarah 工单排最前）；边界语义缺失（"仅限军队系统"的否定/全称不在任何单条工单里——含糊不答也是失败）
- **解法都在索引阶段**：统计摘要**代码算**（确定性计算，D16 回响）、规则卡 **LLM 通读提炼**（作业①）——实测教训：描述性提示词只能提炼归纳（"退伍军人√军医√教师×"），加强为"推断分界标准"后才产出真正的边界规则（"分界是是否隶属军队系统而非具体职业"）——提炼质量取决于源信号与提示词设计
- **RAPTOR 路由（19.2 实证）**：宏观题父摘要明显胜出（0.51 vs 0.41，两叶综合才答得了大盘）；细节题父子几乎平手（0.64 vs 0.64）——单叶组父摘要≈叶子复述，粒度收益为零；组越大、父子差异越大，路由才越有价值
- **GraphRAG（19.3 实证）**：多跳问题"主诊医生所在医院地址"扁平 top-3 连终点句都没捞到（捞回两句"科室"这种语义近邻不搭链的句子），图上三跳 JOIN 一气呵成；实体消歧：扁平检索 B(0.65) vs A(0.62) 浮点噪声定先后，图上两个张医生天然分开
- **生产形状（19.3 Part 3）**：课件 graph_query 要预知关系路径（用户不该知道"主诊医生→就职于→地址"）——真实主流：微软 GraphRAG local search（实体链接→k 跳邻域扩展→LLM 合成，只需跳数不需路径）或 Neo4j text2cypher（LLM 翻译成 Cypher）；19.3 实现了前者最小版：实体卡嵌入链接出种子 [用户,张医生-A] → 双向 2 跳收集 4 条事实 → LLM 合成答案，与预知路径的玩具殊途同归——示例代码偏实际应用规则的首次落地
- **实体消歧 ≠ 词义消歧**：bank 靠上下文嵌入能分（D17 语义地图）；两个同名真人靠图结构/实体知识（图查询天生强制指定节点）
- **有损压缩与分层互补**："如果下雨就改博物馆"拆三元组后 if-then 条件与时间依赖全丢——生产分层：核心信息保留自然语言原文保语义，结构化元数据只管索引检索（D16 Advanced JSON Cards 伏笔回收）
- **决策标准**：查询是"找片段"（退款政策是什么）→ D18 混合检索够；要跨文档综合/多层次导航/多跳推理 → 才值得买单（构建查询两端都烧 LLM 调用）——先量化瓶颈再加索引，与数据库调优同道理

1. "搜索返回 3 个选项"该进记忆吗？（不——本次任务的脚手架，违反选择性；对下次会话毫无价值）
2. 用户先说靠窗后改过道，记忆该怎么存？（当前值=过道，旧值"靠窗"带时间戳进 history——抽象化以最新为准，历史服务时间推理与审计）
3. 轨迹为什么必须 append-only？（审计追溯：改写=篡改账本；KV Cache：回头改=前缀缓存全灭；协议：破坏 tool_call_id 配对链 → 400）
4. L2"多会话检索"和 L1 的区别？（L1 存得准取得回；L2 要跨时间跨对象**找全并推理**——两辆车要问哪辆，不是瞎猜一辆）
5. 为什么记忆注入走 system 而工具结果走 tool 角色？（记忆是跨会话档案属于开发者侧的稳定信息，且放 system 随前缀缓存；工具结果是本次会话的观察——角色体系就是信任等级体系）
6. 认知三分类各对应什么后端类比？（情景=操作日志，语义=配置表，程序=SOP 脚本；它答"存什么"，与层次/格式正交）
7. User as Code 的核心主张？（能确定性计算的别让模型算：带类型对象 + 普通函数规则 + WAL 仅追加 + 检查点重放）
8. 重复陈述同一偏好，仅追加日志会怎样？（同值条目堆叠成脏数据——查询取最新不受影响，但存储爆掉，靠压缩治理：评分→聚类→泛化）
9. mtype（episodic/semantic/procedural）和 15 的 category（preference/fact/activity）什么关系？（正交的两套分类：前者答"认知上是什么、走哪条检索路由"，后者答"业务上是什么"）
10. 为什么不能整篇文档算一个向量？（嵌入长度限制 + 多主题平均稀释向量 + 检索时无关内容灌窗口）
11. 块太小/太大的典型症状各是什么？（太小：断头碎片答一半——得分不低但"7 天内可申请"条件被切丢；太大：区分度消失——"退货到账"与"会员折扣"命中同一块）
12. 余弦相似度为什么用夹角不用距离？（关心方向不关心长短：内容相同一长一短的两段文本方向一致，余弦能正确判语义相同）
13. 查询"退货要多久到账"为什么配送块也得了 0.50？（"要多久"的时长语义撞上配送的 48/72 小时讨论——语义检索的模糊性，BM25 字面精确匹配能补台，明天混合检索）
14. 课本玩具 bigram 词袋和真实 bge 的本质区别？（词袋是共享汉字的字面巧合（≈BM25）；bge 上下文感知看整句——"退货"与"退款"零字面重叠仍 0.68 最高分，还能暴露实验设计错误）
15. TF-IDF 的两个坑与 BM25 的修正？（坑：词频线性涨、长文档占便宜→修：k1 饱和（实测 10 倍词频只换 57% 涨幅）、b 归一化；另 IDF 是变体：词出现在过半文档会变负，须 max(...,0) 设下限）
16. RRF 为什么抛弃原始得分反而更稳健（作业思考题）？（序数可比、基数不可比：余弦 0~1 vs BM25 可到几十，量纲/尺度/分布全不同，加权融合要调参且脆弱；排名是两路共同语言，RRF 天然免疫量纲）
17. RRF 的粗粒度局限（实测）？（稠密第2+BM25第4 与 稠密第4+BM25第2 的得分完全相等（1/62+1/64 对称）——名次之和对"哪路更可信"无感，近并列靠插入顺序裁决→需要重排）
18. 重排为什么只对 top 候选做、不对全库逐对打分？（Cross 逐对过模型是 O(N) 推理，百万文档就炸；Bi 比向量是 O(1) 查询——流水线天生"粗筛快、精排小"）
19. 混合检索的实测取舍？（recall@3 1.00=max(单路)（BM25 单路仅 0.83），但 MRR 0.81<稠密 0.92——top-1 被单路第一名票稀释；所以流水线分工：双路召回→RRF 保 recall→重排修 top-1）
20. 中文 BM25 的命门？recall@k 为何是 RAG 命门？（分词不一致：jieba 把"开发票"切一词对不上"发票"，全 0 瞎排撞大运；金标没进上下文，LLM 连用上它的机会都没有）
21. 计数问题为什么调大 k 也没用？（top-k 捞"语义最近"不是"全貌"——实测捞回 3 份全黑，白猫没进上下文；正解索引阶段离线聚合摘要）
22. 边界语义缺失与最近邻偏置的区别？（前者：规则本身不在任何单条 chunk，否定/全称语义要从全库提炼；后者：语义最近的个案（军医 Sarah）排最前诱导错误类比）
23. 统计摘要用代码算、规则卡用 LLM 提炼，分工依据？（确定性计算别让模型算（D16 回响）；提炼共性要通读理解；实测描述性提示词只能归纳个案，"推断分界标准"才产出边界规则）
24. RAPTOR 什么时候粒度收益为零？（单叶组父摘要≈叶子复述，父子平手（0.64 vs 0.64）——组越大、父子差异越大，路由才越有价值）
25. 多跳问题在扁平库怎么断？（实测起点句命中、终点句没进 top-3，捞回的是"科室"这种语义近邻不搭链的句子——单次检索拼不齐链条；图上多跳 JOIN 一气呵成）
26. 实体消歧与词义消歧的区别？（bank 靠上下文嵌入能分（词义）；两个同名张医生靠图结构/实体知识（实体）——图查询天生强制指定节点）
27. 三元组有损压缩的例子？（"如果下雨就改博物馆"拆三条，if-then 条件与时间依赖全丢；生产分层互补：原文保语义 + 元数据管索引）
28. 何时值得为结构化索引买单？（查询是"找片段"→混合检索够；跨文档综合/多层次导航/多跳刚需才买——构建查询两端都烧 LLM 调用，先量化瓶颈再加索引）
